# Provider connection list read contract

Date: 2 November 2026. Baseline inspected: `c48414a` (PR46 verification closure). Status: BA/SA requirements freeze for a bounded next slice; implementation, independent safety review and QC acceptance remain OPEN. This document changes no code, schema, grants or public route. Coding delegation must follow the safety gate below.

## Authority and scope

The [parent API contract](PROVIDER_CONNECTION_API_CONTRACT.md) owns the exact `Connection` and `List` DTOs, human authority and pagination. The latest [credential storage amendment](PROVIDER_CREDENTIAL_STORAGE_AMENDMENT.md) overrides all historical ciphertext/envelope/rewrap language in that parent: usable credentials live in an external secret manager; the application DB contains only scoped immutable references, versioned keyed verifiers and nonsecret metadata. This contract specializes list projection and the minimum durable evidence required for its health claims. It does not revive reversible DB storage.

Deliver only public `GET /api/v1/organizations/{organizationId}/provider-connections`, its safe read projection, and the reviewed durable health/integrity foundation needed by that projection. Reuse [PR46 options/admission](PROVIDER_OPTIONS_POLICY_CONTRACT.md). No detail, receipt, check, discovery, command, health-write or diagnostic HTTP route; no UI, runtime grant, Agent binding, generation, provider call or live-provider acceptance claim. Trusted evidence publication is an internal capability, never an organization ADMIN capability.

Health infrastructure must exist before exposing this route. Missing observations are a supported state and yield actual `UNAVAILABLE` with null mask. Missing tables, failed queries or unreadable storage are infrastructure failures, not permission to invent observations or silently turn a failed query into an empty result. An unconfigured observer must leave observations absent; no startup seed, all-healthy default, synthetic production vault or fake successful provider adapter is allowed.

## Exact wire and projection

Use existing `ApiResponse`: exactly `{data,meta}`, meta exactly `{requestId}` with server UUID. Data exactly `{organizationId,page,pageSize,total,items}`. `pageSize` is numeric20; page is numeric0..100000; total is the actual nonnegative JSON safe integer count for that organization in the read snapshot, including disabled/unavailable connections. An unrepresentable total fails safe503; never clamp or estimate. Items are at most20 and exactly:

`{organizationId,id,provider,credentialMode,name,options,state,revision,credentialRevision,credentialState,credentialMask,createdAt,updatedAt}`.

No additional field, missing nullable field or internal record serialization is allowed. IDs use lowercase canonical RFC UUID versions1–5/variant2. Revisions are positive canonical decimal JSON strings within signed int64, not JSON numbers. `createdAt`/`updatedAt` are UTC RFC3339 with exactly six fractional digits. Names/options and positive revision relation retain the parent/V022 validation rules. Options are `{}` for OPENAI/GOOGLE_GEMINI, and exactly `{workspaceId}` for ANTHROPIC, including explicit null when absent. Providers/modes remain OPENAI/OPENAI_API_KEY, ANTHROPIC/ANTHROPIC_API_KEY, GOOGLE_GEMINI/GEMINI_API_KEY. State is ENABLED or DISABLED.

`credentialState` is PRESENT or UNAVAILABLE. Mask is the exact constant `"••••••••"` (eight U+2022) only for PRESENT; otherwise explicitly null. Never return prefixes, suffixes, lengths, fingerprints, verifier, locator, external/HMAC key version, health timestamps, observer identity, integrity reason or storage diagnostics. No `connected`, access validity, billing, provider-enabled or runtime-eligible field. Disabling a connection or deployment adapter preserves its metadata and does not alone change credential storage health; do not filter such rows or conflate those independent states.

Sort `created_at DESC,id DESC` with UUID ordering in PostgreSQL, not textual or locale ordering. Count and items use the same organization predicate and snapshot. Page past the end returns200 with empty items and actual total. A malformed selected row is never dropped by an inner join or replaced with another row. Unselected corrupt credential rows do not cause foreign/historical scanning. Separate offset requests may shift under concurrent changes; no cross-request snapshot/cursor promise.

Only optional `page` is accepted; omission means0. Servlet-visible raw query must be exactly `page=(0|[1-9][0-9]*)`, bounded at100000 before integer conversion. Reject bare/empty query, `page`, empty value, duplicate/unknown keys, extra delimiters, signs, leading zeros, whitespace, fractions, exponents, overflow, case variants and percent/plus encodings of names or values. This fixes one canonical spelling; do not rely on framework first-value selection or numeric coercion. No pageSize/filter/search/order parameter.

GET has no body: reject positive Content-Length, any Transfer-Encoding or any input-stream byte. Organization path canonicalization and Accept validation follow PR46, including media specificity and explicit application/json exclusion. Do not accept a body just because a declared length is zero. Fixed public errors never echo query/path/body values.

## Authority, admission and snapshot

Apply the existing session security-context model to the exact collection path. Do not accidentally expose descendants or change options or unrelated route matching. Precedence is:

1. Transport authenticates a human and verifies current enabled account/exact session credential version and same-org ADMIN before strict path/query/body/Accept validation. Missing/nonhuman principal401; stale/disabled account invalidates the session and clears context with401; current human without organization ADMIN403. Unknown organization403, not an existence projection. Lenient scope resolution followed by strict authorized path validation follows PR46.
2. Authorized non-GET returns405 with `Allow: GET`, without admission. HEAD retains the appropriate401/403/405/503 status and has zero body bytes. OPTIONS is405. Unsupported methods do not reach command/CSRF behavior.
3. GET invokes the existing proxied `AdmissionService.acquire(actor,org)` once. Admission completes its own RC writable transaction before strict validation or list read. Options and list together consume120/minute/account/org, across instances; no second route bucket or in-memory fallback. Admitted malformed GET and later503 consume a slot. Unauthorized/unsupported-method attempts do not. Preserve PR46 rollback/no-row-change behavior on429, auth loss, corruption or uncertain admission completion; Retry-After is integer1..60.
4. Strictly validate the wire, then invoke one proxied REQUIRED REPEATABLE_READ read-only service using the same application transaction manager/bound JDBC resource. It rechecks current enabled/version/ADMIN and reads count, selected connection/version rows, integrity and health evidence in that single snapshot. Reject a missing, weaker, writable, autocommit or wrong-resource joined context; no REQUIRES_NEW workaround. Admission authority is not a substitute for this check.
5. Sample PostgreSQL `clock_timestamp()` once at projection evaluation after required database waits, truncated to microseconds, and use it for every item on the page. Do not use transaction-start `current_timestamp`, JVM time or one different clock per item. RR determines row visibility; wall-clock expiry still advances while a transaction waits. H2 clock behavior is structural test support, not PostgreSQL timing evidence.
6. Return a public200 only after read transaction completion succeeds. Controller/completion mapping surrounds the proxy call, including transaction-manager failures. No provisional DTO is written before that boundary; safe503 on read/commit uncertainty, no nested SQL/cause logging or automatic retry.

Authority and storage visibility are linearized at the RR snapshot. A later revocation/rotation/failure commit is not retroactively predicted; a fresh request sees it. These semantics must be stated and tested, rather than claiming current-at-response linearizability. The projection transaction makes no business writes; whole-request admission/session security writes remain deliberate exceptions.

List does not depend on policy provisioning: the DTO contains no policy flags and disabled/unprovisioned adapters do not prevent metadata reading. Do not require a populated policy row or command/dispatch readiness to read this collection. Key-health outage preserves readable safe connection metadata with actual UNAVAILABLE/null mask; missing health never becomes a fake success. Invalid credential storage likewise preserves that safe metadata as unavailable, whereas malformed public connection configuration fails the whole list with safe503. It never reads a local default policy to infer health. Options continues requiring the durable policy as already contracted.

## Minimum durable health and integrity storage

The following is a required logical schema for the next forward migration, not an assertion that V022 already supplies it. Concrete SQL, roles, constraints and publication ports require safety review before delegation. All records are private and contain no usable credential or reversible envelope. Health does not increment configuration/credential revisions or update connection timestamps/events/receipts.

| Record | Minimum fields and constraints |
|---|---|
| Existing immutable credential version | Retain V022 four-part PK and active FK. Freeze the exact external locator, immutable external secret version, HMAC-key version, domain and verifier after insertion. Supported runtime writers cannot UPDATE/DELETE these fields; enforce with reviewed privileges/guarded writer or trigger, not merely Java convention. No health backfill may mutate them. |
| `provider_credential_integrity` | One row per four-part credential-version identity. Exact FK to that retained version. Store bound `external_locator`, `external_key_version`, `hmac_key_version`, `hmac_domain_version`; state VERIFIED_AT_WRITE or FAILED; finite `recorded_at`; positive bigint publication revision. Required fields are NOT NULL; no default VERIFIED state. VERIFIED_AT_WRITE records trusted authenticated preparation/verification of this exact version, not an assertion of per-read authentication. |
| `provider_credential_health` | One row per four-part credential-version identity, same exact FK and bound fields. State USABLE or UNAVAILABLE; required finite `observed_at`, `published_at`, `valid_until`; positive bigint publication revision; trusted publisher identity/fence. `observed_at <= published_at < valid_until <= observed_at + 60 seconds`. No default USABLE state or automatic row. USABLE covers both external-secret-version usability and the recorded historical HMAC-key version, not merely a reachable service/current key. |

For both new records, enforce binding at DB level: add an exact unique target on the version identity plus those bound external/HMAC/domain fields and a matching composite FK from evidence (in addition to, or subsuming, the four-part identity FK). Evidence for another reference or key version must not attach to this credential version. A key ID alone, connection ID alone or latest-version lookup is insufficient. Credential immutability is essential: a reference change requires a new credential revision and evidence. Independent review must inspect actual FK/uniqueness/immutability constraints in PostgreSQL.

Version creation may atomically insert VERIFIED_AT_WRITE only from a trusted prepared result after external preparation succeeds outside DB locks, with exact candidate scope/reference/key versions revalidated at commit. Existing versions get no optimistic backfill from non-null columns, canonical verifier syntax, historical events or successful internal service reads. They remain unavailable until separately authorized verified evidence exists. A typed `Metadata` constructed by a caller is not proof of preparation. Verified repair of a FAILED version is outside this slice; replacement creates a new immutable version with new evidence.

Health/integrity schema must migrate with zero evidence rows and no data-bearing defaults. Missing evidence is a valid unavailable condition; a missing relation or DB access error is503. A restore with old observations uses real expiry; do not restamp observations on startup. Publisher fencing must invalidate results from an obsolete deployment/observer epoch before they can be published.

## Trusted publication and race protection

Only explicitly wired deployment/trusted worker capabilities publish evidence. No HTTP DTO/body/ADMIN role can submit observation status/timestamps, call an observer refresh, clear a failure or select a publisher. Separate database privileges or guarded trusted-writer execution must prevent the public read identity from evidence INSERT/UPDATE/DELETE; the exact deployment role arrangement is a prerequisite. An unrestricted application writer must not be described as a protected observer boundary. Test-only ports/fixtures cannot be production defaults.

Health observer protocol:

1. Outside any held business transaction/lock, capture exact credential identity/reference/key bindings, current health publication revision (or absence), publisher epoch and a DB wall-clock observation-start sample. Perform bounded independent external secret/key-service checks outside DB transactions. Bind that sample to this actual check attempt; never attach a new timestamp to cached/replayed status. Checks must attest usability of that exact immutable external version and historical HMAC version. If component observations occur separately, use the earliest actual observation-start sample and earliest expiry, not the newest signal's clock. No provider call, provider models request or production success stub is permitted. A service ping alone is insufficient. The concrete adapter/check permission/deadline and restore fencing mechanism remain review prerequisites.
2. Publication uses a short RC transaction. Take existing organization-first order, then policy if required by the operation, account/membership if required, scoped connection, credential version, integrity and health rows; never acquire earlier locks after later locks. Internal observer authority comes from the trusted publisher, not an impersonated human. Serialize first evidence insertion through the locked parent/version and uniqueness. Never hold those locks over a network call.
3. After locks/waits, sample PostgreSQL wall clock. Revalidate trusted publisher epoch, immutable bindings and the active parent credential revision, and CAS the captured health publication revision/absence. Increment that durable revision exactly once; require the new observed_at to be strictly later than the prior observation and published_at not to regress. Equal/replayed or older observations do not update status, expiry or revision. Use the post-lock sample as published_at; observed_at remains the DB sample at check start, so a slow check cannot acquire a new60s freshness window. Reject future/nonfinite/reversed timestamps and publication at/after valid_until. valid_until is at most observed_at+60s, never published_at+60s. Clock rollback cannot be clamped into success. On sequence exhaustion or CAS loss, preserve rows and require a new independent observation; no automatic successful upsert.
4. A USABLE publication cannot clear/replace FAILED integrity. Delayed pre-rotation output cannot publish for the replacement or change its evidence; compare exact active revision/reference/key bindings. Stale health writers also cannot overwrite a newer UNAVAILABLE observation. A definite observed outage can publish UNAVAILABLE with the same binding/time/CAS rules; its expiry never becomes implicit success. Missing/expired evidence remains unavailable without a cleanup job.

Integrity publication uses the same lock order, exact binding and active-version/CAS guards. A trusted use/verification path must durably record a confirmed integrity failure for the version it actually verified before claiming that failure is published. Failure for old revision N may be retained against N for history, with exact FK/version checks, but must never overwrite N+1 or its active evidence. FAILED is sticky for that immutable version: later USABLE health, repeated preparation, generic success callback, rename, enable, restart and GET cannot clear it. Race between stale success and confirmed failure must end FAILED, through locked state validation and publication CAS. Do not discard a confirmed same-version failure merely because a health revision advanced.

The existing generic `CredentialBoundary.Failure` is not a confirmed integrity classification: key outages, read outages and consumer exceptions must not be labelled cryptographic mismatch. The reviewed internal producer must distinguish safe typed outcomes without leaking secret details or invoking consumers before verification. Ambiguous failure grants no PRESENT evidence; absent health remains unavailable and existing evidence expires within its original bound. No public change or GET-side verification is authorized to solve this gap.

## Deterministic health projection

For each selected connection, validate safe configuration first. Then evaluate its exact active credential version and evidence in the same RR snapshot using the page clock T:

`PRESENT = structurallyValidActiveMetadata && exactTrustedIntegrityVerifiedAtWrite && !knownIntegrityFailed && exactUsableHealth && observedAt <= publishedAt <= T && T < validUntil && validUntil <= observedAt + 60s && trustedPublisherFenceValid`.

Every conjunction term must be established; unknown is false. Reject nonfinite timestamps, invalid enums/revisions/domains, impossible time ordering or foreign/version/key binding as evidence of availability. No local cache or credentials' creation timestamp substitutes for observations. Equality at validUntil is expired; observedAt after T is unavailable. A positive health observation may change within60s; this is a bounded historical local health statement, not guaranteed next-use success or latent-tamper detection.

| Selected state | Public result |
|---|---|
| Exact structurally valid metadata, trusted verified-at-write integrity, fresh usable exact-key health, no failure | PRESENT / constant mask |
| Missing/expired/UNAVAILABLE health; missing integrity; future/malformed evidence; failed or unknown publisher fence | UNAVAILABLE / null |
| Confirmed integrity FAILED, even with fresh USABLE health | UNAVAILABLE / null, sticky |
| Active metadata missing/malformed or binding does not match the selected version | UNAVAILABLE / null; preserve safe parent in items and count |
| Connection/provider disabled but otherwise healthy credentials | Preserve actual connection state; credential projection follows evidence independently |
| Corrupt public configuration (name/provider/mode/options/state/revisions/timestamps/identity), or DB/query/transaction failure | Safe503 PROVIDER_CONNECTION_UNAVAILABLE; no partial list, row omission or fallback |

The fourth row intentionally differs from the internal persistence list's strict `storedMetadata` failure. Implement a safe query/projection that separates invalid credential storage from invalid public configuration; do not loosen internal dispatch/historical-read validation or bypass the existing current FK. Invalid domain/verifier/reference syntax yields unavailable, never a synthetically repaired `Metadata`. Latent correctly shaped metadata tampering is not detected by GET; trusted verification and immutable storage remain separate controls.

GET has no vault/KMS/HMAC/provider collaborator, secret fetch/decode/verification, readiness/observer refresh, outbox enqueue, retry scheduling, health publication, integrity repair or business mutation. Receipt snapshots and existing historical APIs are not recomputed or changed by this list slice.

## Errors and privacy

Use existing exact `ApiErrorResponse` `{error,meta}`, error exactly `{code,message,details}` with details `{}` and server requestId. All matched feature responses use application/json and Cache-Control:no-store; HEAD has no envelope bytes. Reuse PR46 fixed messages: BAD_REQUEST400 / "Invalid provider settings request"; UNAUTHORIZED401 / "Authentication required"; FORBIDDEN403 / "Request denied"; METHOD_NOT_ALLOWED405 / "Method not allowed"; RATE_LIMITED429 / "Too many requests"; PROVIDER_CONNECTION_UNAVAILABLE503 / "Provider settings are unavailable". This collection has no404 for an empty list, no credential-specific409 and no KEY_SERVICE_UNAVAILABLE from live key calls.

Sanitize service-body and transaction-completion failures, not just mapper exceptions. Never expose/log JDBC bind values, SQL diagnostics, nested exceptions, internal objects, verifier/reference/version values or request secrets. Use explicit public DTOs and redacted internal toString. Controlled captured logs and exact stored-column/value allowlists are required; one secret-sentinel check alone does not prove privacy. No automatic retry after admission or read completion uncertainty.

## Safety gate, unresolved prerequisites and handoff

BA/SA freeze: public wire, authority/admission ordering, RR consistency, health truth table, maximum60s validity, sticky integrity failure and immutable version/CAS binding are normative. No fake health defaults are an acceptable interim implementation.

Before delegated coding, an independent safety reviewer must disposition this concrete design and the proposed migration/publication/read-service boundaries. Required unresolved inputs are:

1. Forward migration SQL with exact composite binding FKs, immutable-version enforcement, publication revisions, finite/time constraints and publisher epoch representation; compatibility with retained V022 rows and migrations.
2. Actual trusted observer identity, database role/guarded-writer arrangement and adapter semantics proving exact external-version and historical-HMAC usability; bounded checks, restart/restore epoch invalidation and deployment provisioning. No implementation currently proves these in V022/CredentialBoundary.
3. Trusted verified-at-write provenance and atomic publication integration for future preparation/rotation, plus safe typed integrity-failure publication. The current generic boundary failure and public-constructible Metadata are insufficient evidence producers. Define restricted repair policy separately; FAILED cannot be cleared here.
4. A scoped public list query/DTO and proxy-completion boundary that implements per-item credential-unavailable behavior while retaining strict internal persistence semantics, same RR resource and current ADMIN checks. Confirm PR46 route matcher/admission reuse without options regression.
5. QC ownership and executable native timing/concurrency/role/privacy fixtures for L01–L20, followed by recorded independent safety and QC dispositions. This document is not an independent approval or an executed test report.

Main may prepare transport/service boundary plans concurrently, but do not delegate implementation against unresolved producer/schema trust assumptions or expose the route before this gate is reviewed. A later deployment may truthfully serve unavailable credentials with empty evidence tables when schema/security prerequisites pass and no real observer is configured; it may never claim PRESENT until trusted durable evidence exists. Documentation freeze does not authorize a merge, deployment, public health writer or provider request.

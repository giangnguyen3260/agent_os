# Provider credential storage amendment — database one-way rule

Status: latest user requirement,31 October2026; supersedes PR40's proposed storage of reversible provider-key envelopes in the application DB. This slice implements only a backend credential boundary and unit tests; no connection API, database writer/migration, deployed secret manager or provider call is delivered.

## Authoritative storage distinction

The user requires tokens to be one-way before database persistence. A provider API key cannot be reconstructed from a hash for outbound authentication. Therefore the usable credential resides in a dedicated external secret manager, protected under its own encryption/access/rotation/backup policy. Application DB credential metadata may contain only exact scoped identifiers, an opaque immutable external-secret reference, versioned keyed HMAC-SHA-256 verification metadata and nonsecret timestamps/state. It must not contain raw credentials, reversible provider ciphertext, wrapped credential DEKs, nonce/tag, base64 disguises, secret command bodies or provider auth headers. These bytes cannot be moved into a DB outbox/audit/receipt/cache as a workaround. This restriction applies to every application-DB table, not just the credential table.

One-way token hashing and reversible secret storage solve different needs. Existing password-reset and invitation migrations already define token_digest fields rather than raw capability columns. This amendment does not assert a completed audit of all session/CSRF serialization or change the accepted authentication/receipt protocols. Audit any newly introduced bearer capability independently. Random high-entropy one-time capabilities may use cryptographic hashes; provider keys can have arbitrary entropy, so do not store an unkeyed SHA256 verifier that enables DB-only offline guesses. HMAC keys remain outside the DB under a separately authorized versioned key service. Password hashing keeps its existing slow password-specific encoder rather than adopting fast HMAC as a replacement.

## Foundation boundary

The backend implementation has explicit secret-manager and managed HMAC-key ports, with no default credentials, fake successful production provider, in-memory production vault or plaintext fallback. Tests may use fake ports under test sources only. Missing dependencies fail closed. The public HTTP API must never expose the internal reference, digest or key version; future serializers return the existing constant mask/allowlisted metadata only.

Preparation consumes transient caller-owned credential buffers and clears them on all paths, validates the exact visible-ASCII length contract, prepares a managed HMAC handle before any external write, writes the usable secret to the external store, then derives a domain-separated MAC bound to scope, returned immutable reference/version and credential bytes, all outside any DB transaction. The returned object is persistence metadata only. Include organization, connection, provider, credential revision, HMAC-key version, exact opaque locator and immutable external secret version in the MAC domain so metadata/reference swaps cannot authorize a credential for another scope. Verify with the recorded historical HMAC-key version and constant-time comparison before exposing a fetched credential to the trusted outbound callback. Clear fetched/temporary buffers after the callback or failure. Java memory cleanup is best-effort: this does not claim every VM/TLS copy can be erased or defend against a compromised application process.

This is an internal primitive, not an authorization service: exact current human/worker authority, accepted revision, deployment policy, lease/deadline and request/receipt checks from the reviewed API contract still belong to the future application service. Possession of a reference/digest is not a grant. No callback may run before integrity and exact scope are verified. Never pass the digest in an Authorization header. Exceptions/toString/logs must not disclose secret bytes or verifier material.

## Future connection transaction and recovery

External secret-manager writes and PostgreSQL commits are not one atomic resource. Future create/rotate must: authorize/parse and probe historical receipt first; prepare historical/current HMAC and external secret outside locks; take the established organization/policy/account/membership/connection locks; reauthorize and reread receipt first; bind prepared external version to exact expected credential revision; atomically commit only allowlisted metadata/event/receipt/outbox. A raced replay must not depend on a working external secret write and must not duplicate connections. No network calls under DB locks.

Prepared external versions need durable preparation identity, immutable scope tags and a bounded reconciliation protocol. If a DB commit is unknown, do not automatically delete the external version or assume it is an orphan. Reconcile committed references/receipts before cleanup, coordinate cleanup with all possible in-flight preparations and never delete a currently referenced or potentially committing secret. Failures leave an explicit reconcile requirement, not a misleading cross-system rollback guarantee. Old versions after successful rotation remain available only for already authorized in-flight reconciliation, subject to explicit reference/retention rules; new dispatch uses only the current committed reference. Application disable never claims remote provider-key revocation.

PR40 API §§5–6 and the old envelope-specific testcase rows are historical proposed storage details where they conflict: no credential ciphertext/wrappedDEK in DB; rewrap happens inside external secret management. Existing scoped command HMAC/replay rules remain required and separate from the new credential integrity HMAC domain. Public connection DTO/authority/UNKNOWN/check/discovery and Figma flows remain unchanged. Reconcile detailed persistence/health/runbook cases with this amendment before writing the application DB schema.

## Required verification

Unit tests cover deterministic scoped MAC, all3 provider kinds, scope/revision/reference substitution, historical key versions, no callback on mismatch/key outage, redacted failures, input/read-buffer cleanup, same-scope same-content locator/version substitution rejection, no default fallback and metadata-only return values. Use an independent known-answer HMAC/canonical encoding oracle, not production code computing its own expected digest. Future actual persistence tests must inspect every stored row and prove that neither plaintext nor any recoverable credential envelope is present. This foundation alone cannot prove that database property because it has no DB writer. Actual secret-manager adapter, deployment key provisioning, restore, integration and concurrency/idempotency/UNKNOWN tests remain required before the feature is accepted.

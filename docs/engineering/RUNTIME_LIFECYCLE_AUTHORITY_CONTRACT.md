# Runtime lifecycle and authority contract — BA-02

Status: proposed implementation contract, coordinator authored; independent BA/SA/QC review pending. Baseline PR38 `cef8d77b402f9fb9473c9458579a9a3cc06c6fb3`, 31 October 2026. This delivery changes documents only. No runtime endpoint, worker, migration, effective permission, activation or provider call is implemented by this contract.

## 1. Compatibility and ownership

V004 Task states remain the canonical persisted vocabulary: DRAFT, READY, RUNNING, WAITING, BLOCKED, IN_REVIEW, COMPLETED, FAILED, CANCELLED. MissionStatus remains CREATED, PLANNING, READY, RUNNING, WAITING_APPROVAL, REVIEW, COMPLETED, FAILED, CANCELLED. TeamStatus remains DRAFT/ACTIVE/ARCHIVED; AgentStatus remains DRAFT/ACTIVE/DEGRADED/SUSPENDED/ARCHIVED. Unknown values fail closed for commands, without inventing a repair.

MISSION_STATE_MACHINE.md v0.1 is historical conceptual design. Its Task PENDING maps only conceptually to dependency-blocked preparation; ASSIGNED becomes a runtime assignment/claim record, not a new Task status; REVIEW becomes IN_REVIEW; DONE becomes COMPLETED; REWORK becomes an immutable reviewer decision plus a new attempt, not a persisted Task status. WAITING_APPROVAL is a Mission state and a typed Task wait reason, never a new Task status. These are design correspondences, not data migration rules. Do not infer dependencies, attempts, authors or execution success from legacy status or free text.

Existing rows, configuration history and receipts stay unchanged. Existing DRAFT edit/owner/dependency and intake gates retain their respective frozen contracts. No readiness backfill, automatic activation, historical attempt synthesis or reinterpretation of configuration ownership as a worker claim. Legacy non-DRAFT rows lacking runtime provenance remain readable as saved state; runtime commands return a safe unsupported/legacy conflict until an explicit adoption contract exists. Initially only DRAFT tasks explicitly admitted through a newly accepted runtime plan are executable.

Runtime transitions belong to Orchestration; only its transactional application service writes authoritative state. Human commands request transitions; workers submit lease-bound observations; models propose plans/output. Neither model text nor arbitrary metadata updates can set lifecycle state. UI uses server-derived capabilities with fresh authorization at command time.

## 2. Required runtime records and invariants

Future migrations must introduce an accepted immutable Plan revision, scoped plan-task membership/config snapshot, logical execution Run, numbered Attempts, runtime assignment/claim, typed blockers, artifact/output versions, review decisions, usage/reservations and durable dispatch records. These records do not yet exist. Names and exact DTO/schema belong to each engineering slice; semantics below are required.

Plan revision binds exact organization/Team/Mission, task identities, complete validated DAG, configured owners, input/edit/owner/dependency revisions and relevant parent lifecycle. Acceptance revalidates this snapshot atomically. Regeneration is a proposal; never silently deletes or overwrites manually created tasks or existing command receipts. First runtime version admits reviewed existing DRAFT tasks only; generated new tasks must first be explicitly persisted through an approved planning command. An accepted plan is immutable. Acceptance itself does not admit tasks or make them executable. Explicit Mission start atomically validates the complete plan and changes every admitted DRAFT task to READY or BLOCKED before exposing any dispatch; no dependent admitted task remains editable DRAFT while roots run. Any stale configuration rejects the entire start without partial admission. Existing PLANNING editor prohibition is preserved: initial planning uses immutable proposals, and corrections occur through a separately contracted proposal-edit/reject/regenerate flow rather than widening DRAFT editor gates. A proposal cannot bypass existing editor restrictions by overwriting saved configuration. Changing admitted configuration invalidates start; while running, runtime-version tasks cannot accept configuration writes unless a future versioned replan contract explicitly permits them. Unrelated drafts can continue to follow existing intake rules.

Run identifies one admitted task execution under one accepted plan/configuration. Attempts number actual tries; each retry/rework gets a new immutable attempt identity. One valid claim/attempt per task at a time; assignment is not execution. A claim is a bounded lease plus monotonically fenced token; stale workers cannot publish state/output or settle resources. Claim loss never proves a provider/tool action did not execute.

The logical Run represents the full task lifecycle; an Attempt represents an actual execution try. Run states are CREATED, BLOCKED, RUNNING, WAITING, IN_REVIEW, REWORK_REQUIRED, COMPLETED, FAILED, CANCELLING, CANCELLED. WAITING has a typed reason, including external input and approval. No claim is created while blocked. The following mapping is normative; Task/Run/control/claim/pending fields are updated atomically in the same transition transaction.

| Event | Task / logical Run | Attempt consequence |
| --- | --- | --- |
| Atomic admission | READY/CREATED or BLOCKED/BLOCKED | No outbound attempt yet |
| Queued eligibility lost | READY → BLOCKED; CREATED → BLOCKED | No call permitted |
| Blockers resolved | BLOCKED → READY; BLOCKED → CREATED | Fresh queued eligibility, never direct resume without a claim |
| Fresh fenced claim starts work | READY → RUNNING; CREATED → RUNNING | New numbered CREATED → RUNNING attempt |
| Safe input/approval wait | RUNNING → WAITING; RUNNING → WAITING with typed reason | Approval wait: RUNNING → WAITING_APPROVAL; input wait: RUNNING → WAITING_INPUT; same attempt retained only at a recorded safe continuation boundary |
| Safe continuation | WAITING → RUNNING; WAITING → RUNNING | Valid current claim and exact continuation; WAITING_APPROVAL/WAITING_INPUT → RUNNING, no duplicated outbound action |
| Wait rejected or resume ineligible | WAITING → BLOCKED; WAITING → BLOCKED | Close quiescent attempt as FAILED with reason or through CANCELLING → CANCELLED; unresolved outbound effects remain UNKNOWN and prohibit new claims |
| Ambiguous call or authority loss | RUNNING → BLOCKED; RUNNING → BLOCKED | Attempt UNKNOWN if remote effect uncertain; otherwise reconcile definite result without automatic progression |
| Submitted generation | RUNNING → IN_REVIEW; RUNNING → IN_REVIEW | Current attempt SUCCEEDED; output awaiting human acceptance |
| Accept current output | IN_REVIEW → COMPLETED; IN_REVIEW → COMPLETED | Attempt remains SUCCEEDED; immutable review decision |
| Request rework | IN_REVIEW → READY; IN_REVIEW → REWORK_REQUIRED → CREATED atomically with decision | Prior SUCCEEDED attempt retained; next claim creates a distinct attempt |
| Definite failure / explicit retry | RUNNING → FAILED; RUNNING → FAILED; then FAILED → READY and FAILED → CREATED if eligible | Prior FAILED attempt immutable; retry gets a new identity |
| Cancellation request | Task retains current state; every unfinished Run state, including CREATED/BLOCKED/FAILED/REWORK_REQUIRED, → CANCELLING | Stop queued claims/new calls; live/waiting attempt → CANCELLING or UNKNOWN pending reconciliation |
| Cancellation acknowledged | Task → CANCELLED; CANCELLING → CANCELLED | Every outbound effect/accounting reconciled, every attempt terminal, no live claim or executable pending dispatch; preserve actual immutable SUCCEEDED/FAILED outcomes and mark only actually cancelled attempts CANCELLED |

Attempt states: CREATED, RUNNING, WAITING_APPROVAL, WAITING_INPUT, SUCCEEDED, FAILED, CANCELLING, CANCELLED, UNKNOWN. CREATED → RUNNING or CANCELLED; RUNNING → typed wait/SUCCEEDED/FAILED/CANCELLING/UNKNOWN; typed wait → RUNNING/FAILED/CANCELLING; CANCELLING → CANCELLED/UNKNOWN or a verified already-incurred result. UNKNOWN resolves only through the trusted reconciliation service to a verified SUCCEEDED/FAILED/CANCELLED result; it cannot resume an outbound action. SUCCEEDED/FAILED/CANCELLED are immutable terminal attempt outcomes. Reconciled success records evidence but does not auto-progress a blocked/cancelling Task or accept an output. A new attempt is allowed only after all earlier effects are accounted for and a current authorized explicit continuation/retry is safe. COMPLETED/CANCELLED Runs are terminal. Retryable FAILED Run/Task can be cancelled; Mission FAILED remains terminal. Exact DTOs and transaction guards are finalized in BA-07 without contradicting this mapping.

Lease expiry atomically invalidates the old claim token. Cancellation takes precedence in either serialized ordering: if cancellation has committed, preserve Run CANCELLING and the retained Task projection. Mark uncertain effects UNKNOWN on the attempt/runtime blocker ledger without violating the pending-field invariant of the retained Task state. Close/reconcile a proven quiescent waiting attempt without issuing a continuation claim. Trusted reconciliation settles actual outcomes before the guarded CANCELLING → CANCELLED acknowledgment. If cancellation serializes after lease-loss processing, it likewise moves the resulting unfinished Run to CANCELLING and fences every continuation. The following normal BLOCKED/WAITING lease branches apply only when cancellation is not pending. If a call may be in flight, Task/Run become BLOCKED with OUTCOME_UNKNOWN and the attempt UNKNOWN; replacement execution is forbidden pending trusted reconciliation. For a proven quiescent safe human wait with no in-flight action, preserve Task/Run WAITING and the same WAITING_INPUT/WAITING_APPROVAL attempt; a separately authorized continuation claim can be acquired with a newer fencing token bound to that exact attempt/continuation after fresh authority/control checks. This continuation claim neither creates an attempt nor repeats an already authorized call. Renewal/reacquisition is distinct from fresh-attempt claiming; no new lease can supersede an unresolved live/UNKNOWN action. A reconciled successful attempt remains on a BLOCKED Run until an authorized explicit disposition either submits the verified exact output for review without another provider call (BLOCKED → IN_REVIEW for Task/Run), or discards it with a recorded reason and requests a permitted new attempt. This is not BLOCKED → READY with a retained live attempt. The complete §2 mapping and these guarded extensions are authoritative; §3 summarizes them.

Cancellation commits a durable control revision and fences all not-yet-authorized dispatch/calls and ordinary progression. Claim, continuation, outbound-call authorization and ordinary result-publication transactions check this revision under the same serialization protocol. A committed outbound authorization record is the linearization point: calls authorized before cancellation may still reach the provider and require reconciliation; calls ordered afterward are denied. This is not a promise to atomically cancel a remote request across a network gap. Success racing a committed cancellation cannot advance Task/Run to IN_REVIEW/COMPLETED. Trusted reconciliation can retain actual output/effects and settle usage without progression. Cancellation acknowledgment requires every attempt terminal, all effects/accounting resolved, no live claim and no executable pending dispatch; preserve SUCCEEDED/FAILED attempts rather than relabelling remote outcomes CANCELLED. The logical Task/Run can be CANCELLED while retaining those historical outcomes.

All runtime writers of graph-bound Task metadata, acceptance/admission and snapshot validation must join the existing dependency serialization protocol: organization row FOR UPDATE first, then established account/membership/parent locks and canonically ordered Task locks. Re-read scope, revisions and authority after waits. Never obtain the organization mutex after Run/claim/Task locks. Freeze multi-account/Agent/resource locking compatibly before implementation; a more concurrent replacement requires a separately reviewed protocol covering all existing participants. Network calls remain outside transactions.

A trusted reconciliation service has narrow independent authority to verify immutable action/provider locators, ingest untrusted late observations, record actual usage/effects once and settle reservations using the unique action/attempt settlement identity. Stale/revoked workers cannot advance lifecycle, settle directly or authorize new effects. Reconciliation cannot retry actions or accept output; current execution grants are mandatory for any new outbound action. Revocation does not erase already-incurred effects or accounting duties.

Every accepted transition atomically records prior/current state, authenticated actor/service identity, revision, reason, timestamp, safe audit and required outbox event. One command receipt per defined actor/scope/key namespace with a canonical body digest; matching body replays and a different body conflicts. Preserve existing command namespaces rather than adding body to the uniqueness key; expected revision and idempotency are separate. Matching durable receipt replays after fresh authority/scope checks but before mutable-state checks. Failed commands and rolled-back events produce no partial business effects. Never hold a database transaction across model/tool/network calls.

## 3. Task transitions

| From | To | Authoritative trigger / conditions |
| --- | --- | --- |
| DRAFT | READY | Explicit accepted-plan admission/start; all prerequisites accepted COMPLETED, active eligible owner, current grants/provider, budget and execution envelope valid |
| DRAFT | BLOCKED | Explicit runtime admission records a real unresolved dependency/input/config blocker; never materialize arbitrary legacy status as provenance |
| READY | RUNNING | Worker obtains current valid claim; start transaction rechecks eligibility and reserves resources before outbound execution |
| READY | BLOCKED | Eligibility revoked or dependency/input/resource prerequisite no longer satisfied before execution; no provider action |
| RUNNING | WAITING | Required approval or external input is durably recorded and the worker is at a safe wait boundary |
| RUNNING | IN_REVIEW | Output/artifact and actual usage committed for the current fenced attempt; required completion data available |
| RUNNING | BLOCKED | Ambiguous effect, authority loss or lease expiry; atomically fence claim and set typed pending fields; UNKNOWN effects prohibit new calls |
| RUNNING | FAILED | Definite recorded failure, not an unknown outbound outcome |
| WAITING | RUNNING | Exact wait resolved and current attempt safely resumable; fresh grants, input/config binding and resources revalidated |
| WAITING | BLOCKED | Rejection/expiry, invalidated context or unsatisfied safe-resume condition; preserve why and who can resolve |
| BLOCKED | READY | Authorized resolution verifies all blockers, every prior attempt terminal with effects accounted for, prerequisites and current execution envelope; retained WAITING_INPUT/WAITING_APPROVAL attempts cannot enter this fresh-attempt path and may only use the separately authorized same-attempt WAITING continuation |
| BLOCKED | IN_REVIEW | Authorized disposition of a reconciled SUCCEEDED attempt submits its verified exact output without a new provider call; no cancellation or unresolved effect |
| IN_REVIEW | COMPLETED | Authorized reviewer accepts the exact current immutable output version; Agent self-report cannot complete Task |
| IN_REVIEW | READY | Authorized rework decision; close old attempt and schedule a new bounded attempt, with reason and remaining limits |
| FAILED | READY | Explicit permitted retry after definite failure; fresh review of retry consequences, remaining limits and no unresolved side effects |
| Nonterminal | CANCELLED | Authorized cancellation reconciles all queued/live attempts and side effects first; UI shows cancellation requested until this completes |

COMPLETED/CANCELLED do not reopen in v1. FAILED permits explicit bounded retry; Mission FAILED is terminal in v1. Resolve input through a typed runtime input contract, not the DRAFT configuration editor. Runtime eligibility is stricter than saved DAG validity: every required prerequisite must be included in the complete admitted DRAFT closure or have explicitly supported compatible runtime completion provenance. In v1, unsupported legacy prerequisites reject plan acceptance/start with a safe unsupported-prerequisite conflict and no writes, rather than a permanently unresolvable ordinary wait. Never drop an edge or synthesize completion. A correction uses existing draft gates when eligible; planning-time proposal correction follows the separate proposal contract.

Dependencies require accepted completion from the current compatible plan/run, not merely an old persisted COMPLETED label. No implicit COMPLETE on a model response or approval decision. Resource exhaustion before claim is BLOCKED; a transient scheduled retry can be displayed with a real next-attempt timestamp but must not hide automatic cost-bearing attempts.

V004 pending fields are populated exactly for WAITING/BLOCKED: nonblank safe human reason, waiting_since, resolver. All other Task states keep these fields null. Runtime blocker records additionally store stable reason codes, safe source reference, required capability and resolution state. Legacy reason/resolver strings are display-only and cannot confer permissions or identify an approval.

Initial reason codes: DEPENDENCY_UNSATISFIED, INPUT_REQUIRED, APPROVAL_REQUIRED, APPROVAL_REJECTED, APPROVAL_EXPIRED, OWNER_UNAVAILABLE, AUTHORITY_REVOKED, PROVIDER_UNAVAILABLE, BUDGET_EXHAUSTED, RATE_LIMITED, EXECUTION_PAUSED, OUTCOME_UNKNOWN. Multiple blockers remain individually recorded. UI shows actual reason(s), responsible role, wait start and authorized action; never infer a link from free-text matching. RATE_LIMITED must show real retry eligibility/time when known; unknown timestamps stay unavailable.

## 4. Mission transitions and independent controls

CREATED → PLANNING on authorized planning command; PLANNING → READY only after accepting a validated current plan; PLANNING → FAILED on explicit abandonment or exhausted configured planning limit. Rejected proposals remain proposals; regeneration is bounded and charged. READY → RUNNING on explicit start with at least one admitted task and a valid execution envelope. Model generation never starts workers automatically.

RUNNING → WAITING_APPROVAL only when no independent task can proceed and outstanding approvals are the reason. A single waiting task must not falsely label all concurrent Mission work paused. WAITING_APPROVAL → RUNNING whenever independent executable or active work exists, even with other approvals pending. Recompute this aggregate after task/claim/blocker/control/approval changes under the compatible transaction protocol. If nothing is executable, WAITING_APPROVAL applies only when approvals are the sole outstanding blocker category; mixed input/resource/control waits retain RUNNING with explicit runtime blocked/paused metadata, not a new persisted Mission state. When the sole-approval predicate becomes false with no executable task (including rejection or an additional input/resource blocker), WAITING_APPROVAL also returns to RUNNING with explicit blocked metadata; this is a deterministic aggregate projection. Status never authorizes a claim or bypasses execution pause. Rejection normally blocks the affected task; it fails the Mission only under an explicit plan-critical failure/abandonment policy. RUNNING/WAITING_APPROVAL → REVIEW when all required execution outputs are submitted, with no live/UNKNOWN attempts or unresolved required blockers; task-level review can occur earlier. REVIEW → RUNNING on authorized bounded rework; REVIEW → COMPLETED only when every required task output is accepted. Nonterminal → FAILED only after definite plan-critical failure/abandonment and reconciliation; nonterminal → CANCELLED only after cancellation reconciliation. COMPLETED/FAILED/CANCELLED are terminal in v1. A failed Mission requires a new Mission or a separately specified recovery feature, not hidden reopening.

Intake pause remains the existing task_intake_paused/version command: it controls new tasks and the existing conservative draft editors, not workers. Execution pause is a new independent runtime control: stop new claims/calls at safe boundaries; preserve in-flight side effects and show pause requested until the safe boundary is acknowledged. Cancellation is likewise an explicit request, not instantaneous deletion. Explicit Mission start is one organization-first serialized transaction: fresh locked authority/scope checks and complete accepted-plan membership/configuration validation; Mission READY → RUNNING and runtime control revision; every admitted Task state/pending projection and logical Run; command receipt, safe audit and required dispatch/outbox records. No claim or network call occurs before commit. Any stale snapshot, lost authority or insertion failure rolls back the whole start with zero admission/dispatch. A snapshot mismatch always conflicts; an unchanged configuration with a current execution-envelope blocker may be atomically admitted BLOCKED under the frozen start policy. Plan acceptance binds both its validated pre-acceptance parent snapshot and the exact post-acceptance READY parent/control revision it writes. Start compares the latter, permitting only that recorded PLANNING → READY transition, not arbitrary later parent changes. Duplicate start follows actor/scope/key/body receipt semantics and creates no extra Runs.

Mission status alone cannot encode these controls; introduce durable runtime control state with its own revision before exposing UI actions. Team becoming ineligible (including ARCHIVED), Agent suspension or grant revocation prevents new claims/calls; already in-flight work is reconciled without representing it as safely cancelled merely because a flag changed.

## 5. Proposed v1 authority matrix

The new runtime roles below are proposed conservative v1 policy, pending explicit product freeze in each implementation contract; they are not an assertion of prior user approval or a change to existing endpoints. Every human capability requires current enabled credential-matching account, current organization membership, exact tenant/Team/Mission/Task scope and applicable resource grant. Agent execution uses scoped service identity and a current valid claim; human browser sessions are not worker credentials.

| Operation | ADMIN | MEMBER | Agent/model/worker |
| --- | --- | --- | --- |
| Existing metadata reads | Existing contracts | Existing contracts | No inherited human read access |
| Provider secrets, grants, activation/suspension, budget policy | Explicit ADMIN command; never return raw secrets | Denied | Denied |
| Plan generation/review/accept; start/pause/cancel; explicit retry/input | ADMIN in initial runtime version; fresh eligibility at commit | Denied until separate scoped delegation contract | Manager may propose; no self-authorized lifecycle command |
| Tool/model invocation | Not a browser bypass; gateway policy still required | Same | Current assignment, scoped grant, policy and resource reservation required at call boundary |
| Review output | Current ADMIN explicitly reviewing the exact Agent-generated output version | Denied until reviewer-grant contract exists | Reviewer Agent may recommend; cannot finalize acceptance in initial version |
| Decide runtime approval | Action-specific explicit current grant, scope, risk, expiry and separation rules; ADMIN alone insufficient | Same explicit eligible grant under frozen action contract | May request; cannot self-grant or approve |
| Report attempt result | No arbitrary human status edit | Denied | Current fenced claim and exact attempt/input/output identity required |
| Cross-tenant access or arbitrary state PATCH | Denied | Denied | Denied |

Initial runtime acceptance is an explicit human ADMIN decision; a reviewer Agent only recommends, and the producing Agent cannot accept its own result. Do not infer a new two-human requirement or alter existing PUBLISH_PREVIEW decision eligibility. Runtime approval actions need their own frozen supported-action contract; existing approval rows/grants cannot authorize arbitrary tool payloads. Review and approval are distinct decisions.

Provider API keys require authenticated reversible encryption with a managed key reference and rotation, never a one-way hash that prevents use. Passwords and verification capabilities remain one-way hashed. No secrets/private input/raw model/tool payloads in safe audit or ordinary Trace metadata. Run input/output inspection and artifact downloads require dedicated scoped read contracts, not unrestricted Trace payload access.

Typed escalation is required for exhausted limits, unavailable reviewer/input resolver and unresolved outcomes. Each durable work item binds reason/limit, organization/Team/Mission/Run/Attempt/output version as applicable, responsible capability and notification identity. The affected contract must enumerate exact permitted human resolution commands (such as supply input, abandon/cancel or explicitly propose a revised plan) and their current authority/version checks. Manager may recommend, never self-grant authority, reset ceilings, accept its output or trigger an unapproved side effect. If no eligible resolver exists, retain a visible unresolved escalation without inventing a recipient, automatic retry or silent failure. Existing PUBLISH_PREVIEW self-issuance/self-decision rules remain unchanged.

## 6. Limits, uncertainty and version fences

Before first live execution freeze explicit token/cost, concurrency, duration, retry/rework and planning ceilings. Existing Team/Agent requested settings are inputs to policy, not proof of allocation. Reserve budget atomically across organization/Team/Agent/Mission; settle actual usage against the reservation once. Unknown provider cost retains a conservative reservation and explicit unknown status pending reconciliation; never reset to zero. Rate/concurrency enforcement is required before call, not merely a dashboard.

Queue delivery is at-least-once; claim/outbox/receipt fencing prevents duplicate committed state, not magically exactly-once network effects. For supported outbound actions require provider idempotency/reconciliation when possible. An ambiguous side-effecting result blocks automatic retry; recover using the exact action locator and current authority. Lease expiry, timeout or worker restart alone is not proof that retry is safe. Pure generation retry still consumes money and requires bounded explicit policy and a new attempt.

Configuration, plan, runtime transition, control, claim and output revisions are separate. A graph fingerprint is not an execution-plan acceptance. Intake revision is not execution pause. The backend rechecks grants/credential version at claim, immediately before each outbound call and before accepting fenced results; no promised atomic cancellation of a network call already accepted by a provider. UI clears private data on actor/scope/authority change and fences late success/error by identity, revision and generation.

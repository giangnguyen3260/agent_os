# Provider connection persistence slice

Date:1 November2026. Implementation scope: internal authenticated JDBC persistence for prepared provider-connection metadata. Based on PR41 closure1463275f40fd09d8a4bdabb2f1f411ef4ef8c0cf. No HTTP controller, Angular feature, public command/receipt protocol, actual vault adapter or provider call in this slice. PR40's full API contract remains a later application boundary, superseded by the database-one-way storage amendment.

## Storage and methods

Add V022 migration with provider_connections, provider_credential_versions and provider_connection_events. The application database may hold scope/provider/mode/name/options/state/revisions/timestamps, opaque immutable external locator/version, HMAC-key version and canonical32-byte HMAC encoded base64. No plaintext key, recoverable encrypted key, wrappedDEK, nonce/tag, raw request/body or secret-bearing outbox. Credential versions are immutable and retained; no deletion/remote cleanup method. Every active connection references an exact matching organization/connection/provider/credential-revision row. Historical versions remain independently readable internally for later reconciliation, never as a public credential API.

Internal Spring service/repository methods: create from CredentialBoundary.Metadata at revision1; scoped get/list; rename; replace prepared credential with expected configuration revision and next credential revision; disable/enable. Inputs are authenticated HumanIdentity plus exact org/id/revision and typed prepared metadata, never a char[], apiKey String or reversible payload. This layer cannot cryptographically prove that a metadata object came from prepare; the trusted future application service must prepare with CredentialBoundary and independently verify command authority/correlation before invoking it. Do not expose this internal object through Jackson or map an HTTP body directly to it.

Fresh enabled credential-matching current same-org ADMIN is required for every operation; MEMBER/foreign organization denied403, unauthenticated401, missing exact scoped connection404. Recheck authority after waits. Writes serialize organization row first, then authenticated account/membership and connection rows with consistent ordering; no network/key-service/vault call inside any transaction. Reads use a consistent scoped snapshot without write-side effects. Row validation rejects malformed stored metadata generically; no current metadata lookup from foreign references.

Create is ENABLED, configuration revision1, credential revision1. Provider/mode/workspace are immutable; type OPENAI or GOOGLE_GEMINI has null workspace; ANTHROPIC supports null or strict wrkspc_ ASCII identifier. Name normalized nonblank1..100 Unicode codepoints, reject controls/line separators/unpaired surrogates. Scope/reference/digest comes from typed PR41 metadata; store exact validated values and record HMAC-domain versionv2 explicitly. Current credential row and parent connection commit atomically.

Rename increments configuration revision only. Replace credential increments both revisions exactly1, matches org/connection/provider and expected next credential revision, retains prior versions and preserves name/options/state. Disable/enable increments configuration revision only; no implicit vault/provider action. Same normalized name or same requested state is409 NO_CHANGE. Stale revision is409 REVISION_CONFLICT; overflow409 REVISION_EXHAUSTED; no wrap. State-changing success updates timestamp and inserts one immutable revision event atomically. Event snapshots contain only safe configuration names/provider/workspace/state/revisions, actor/time; no locator/verifier/key version or provider secret. Forced event failure rolls back parent and credential version. No mutations to existing Team/Agent/Mission/Task/grant/session/history tables.

Scoped list fixed20,page0..100000, actual count, stable created_at DESC,id DESC, out-of-range empty retains total; no arbitrary pagesize/search. Every selected row validates exact metadata and parent-version relation; selected corruption fails closed, no silent omitted connection. This is internal data access, not the full public Connection/Detail/Receipt DTO contract.

## Deliberate application boundary

This primitive does not accept or infer an idempotency key and does not implement public command receipts or exactly-once create. Duplicate create under an existing ID conflicts safely; never silently upsert/change an existing connection. Callers must not blindly retry with a new identity after an uncertain commit. Future HTTP orchestration must perform actor/scope/key/body receipt recovery before preparing secrets, retain stable connection/preparation identity, and commit its own receipt plus this mutation within one compatible transaction (joining REQUIRED propagation), under the reviewed key-preparation/authority/revision protocol. Without that wrapper these methods are not a complete user-facing save/recovery feature.

Prepared external secrets and DB transactions are separate resources. A failed or uncertain DB commit must not trigger remote deletion here. Future reconciliation checks committed refs/receipts and in-flight preparations before classifying an orphan. Retained versions are not permission for new dispatch; current authorization/version/lease/limits must be checked in the future runtime service.

## Normative clarifications after independent R1–R4 review

R1 mapping: organization/connection/provider/credentialRevision are PR41 Scope fields; external_locator/external_key_version exactly Reference.locator/keyVersion; hmac_key_version exactly Metadata.macVersion; verifier exactly Metadata.digest; hmac_domain_version literal v2. Locator, external version and HMAC-key version match `[A-Za-z0-9_./:@-]{1,256}`; digest must decode to32 bytes and reencode to exactly the same44-character standard base64. Reject mismatched metadata/reference scope, nonpositive revisions or unsupported provider before mutation. Persistence cannot prove reference provenance or semantic non-secret content: only trusted prepared metadata is admissible, never an HTTP field mapping. No arbitrary options JSON. Exact modes: OPENAI_API_KEY, ANTHROPIC_API_KEY, GEMINI_API_KEY mapped to their respective providers. Workspace null except optional Anthropic `wrkspc_` plus1..128 ASCII letters/digits. Name strips surrounding Java Unicode whitespace/space characters and U+FEFF; preserve other characters without case folding or Unicode normalization; reject empty, controls, U+2028/U+2029, unpaired surrogates or >100 Unicode codepoints. Retained/event names follow the same rules. Wider SQL name storage may accommodate UTF-16 H2 differences, but every service read/write enforces100 codepoints. Safe failure codes/messages never include input/verifier/reference, JDBC bind values or exception causes.

R2 authorization/transactions: every operation checks HumanIdentity.id, current enabled account and exact credential_version, plus current organization ADMIN membership. Unauthenticated401; authorized-organization check403 precedes resource existence404; never lookup/project a foreign connection to explain a denial. Write lock order: organization FOR UPDATE → actor human_accounts FOR UPDATE → same-org organization_memberships FOR UPDATE → scoped provider connection FOR UPDATE; re-read enabled/version/role after waiting. Single actor, no multiple-account lock set in this slice. Inspect existing role/removal/disable/reset writers at freeze: they must lock account/membership compatibly or not acquire earlier locks after later ones. Mutation requires the existing application transaction manager and same JDBC DataSource, READ_COMMITTED, REQUIRED; joined outer transactions must use that same manager/data source/isolation and already obey the order. Reject unsupported actual isolation before mutation, do not silently run a writer in an outer repeatable-read snapshot. A returned value in an outer transaction is provisional until outer commit. Every domain/SQL/event failure marks joined work rollback-only; caller failure after return rolls back caller marker plus all new/changed rows. No REQUIRES_NEW or independent connection/commit.

Read authority/count/selected rows are one REPEATABLE_READ read-only snapshot; a joined reader must already provide compatible snapshot isolation. Validate actual isolation rather than silently joining weaker isolation. Authority is linearized at that snapshot; a later revocation is not retroactively predicted, and the next operation reauthorizes. No read-side vault/key/network work or business writes.

R3 physical relation: current connection (ENABLED or DISABLED) has a non-null positive credential revision and an immediate composite FK `(organization_id,id,provider,credential_revision)` to the exact immutable version tuple `(organization_id,connection_id,provider,credential_revision)`. Version tuple PK plus organization FK and globally unique parent connection ID prevent a current pointer selecting another tenant/connection/provider/revision. Insert version first, then parent and event in the same transaction; replace inserts the next version before atomically advancing the parent pointer. This intentionally avoids a cyclic reverse FK for H2/PostgreSQL immediate-constraint compatibility. No claim that every unreferenced credential version is independently forced by DB to have a parent: supported service operations never commit such orphans, and reads require authorized scoped parent existence before accessing versions. Retained historical references are restricted internal data, not a new historical-read API in this slice. No cascade deleting versions/history; no supported UPDATE/DELETE of immutable version/event rows. Direct DBA tampering is outside writer-privilege guarantees and must not be mislabelled prevented by the primitive; selected records still validate/fail closed. Current-FK violations, dangling pointers and invalid disabled current pointers must be rejected in native PostgreSQL. Use LEFT JOIN or equivalent complete selected-parent validation, not an inner join dropping malformed connections.

R4 outcomes: CREATE writes exactly1version+1parent+1CREATE event; duplicate global connection ID yields409 CONNECTION_CONFLICT without foreign lookup/disclosure. It is not a public idempotent replay. Every update validates expected configuration revision first, then operation no-change, then overflow before actual mutation. ROTATE additionally requires exact next credential revision and matching immutable org/id/provider; check both independent revision ceilings. Rename/state updates preserve current credential and all prior rows. Each successful CREATE/RENAME/ROTATE/ENABLE/DISABLE writes exactly one revision event; all rejections write zero events and preserve all rows/timestamps. Store safe after-configuration snapshot in each event: org/connection/provider/mode/name/workspace/state/configuration revision/credential revision/actor/time only; no credential material or verifier/reference metadata. An event at each committed revision forms the initial configuration chronology; this is not a separately exposed before/after history viewer. A failed create/rotate/event/constraint or outer rollback preserves every preexisting row and commits no prepared version/parent/event. A method failure is a definite local rejection only when the transaction outcome is known; uncertain outer commit remains for the future receipt/orchestration layer and must never cause remote compensation or automatic fresh-ID retry.

Acceptance tests must distinguish these exact DB invariants from service-only rules: compare complete new-table schema/rows, not substring-sentinel checks alone; test all providers, current FK rejection, retained versions, stale+no-op precedence, counter ceilings, create and rotate event-failure rollback, joined outer rollback, true PostgreSQL competing updates and authority loss while observed waiting. Existing application tables must remain unchanged under controlled fixtures; no network collaborator is invoked.

## Transaction-completion privacy boundary (F4 clarification)

Cause-free fixed ProviderConnectionFailure protects service-body validation/statement/mapping failures only. Spring may commit an owned transaction after the proxy method body returns, and an outer caller may commit much later. This internal primitive does not intercept/sanitize those transaction-manager completion exceptions or framework/JDBC logging; no universal safe-completion-diagnostics guarantee is claimed here. A later consuming application/privacy boundary must surround the actual outer transaction completion, redact nested failures and bind any uncertain outcome to its receipt/reconciliation protocol. It must never log raw SQL/bind diagnostics or describe a possibly committed operation as definitely rejected. Keep deployment parameter/SQL exception logging disabled for this metadata path; actual log-capture/injected-completion-failure acceptance remains an explicit application-layer gate.

No HTTP route exposes this primitive, and no provider plaintext enters its methods. This narrows the current acceptance claim rather than treating a method-body catch as protection for a future caller's commit. Future public APIs must not be enabled without that completion boundary. Existing provider primitive rollback tests demonstrate known rollbacks only; they are not proof that all distributed failures have a known outcome.

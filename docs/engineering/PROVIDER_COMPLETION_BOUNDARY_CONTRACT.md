# Provider receipt transaction-completion boundary

Date:1 November2026. Bounded internal follow-up to PR44. This explicitly constructed Spring service surrounds actual transaction completion for prepared provider-configuration receipt execution and explicit own-receipt lookup. It does not expose HTTP, parse requests, prepare HMAC/credentials, call key/vault/provider services, retry commands, delete external secrets or implement policy/health/rate/audit/public DTOs. Prior internal receipt arguments and trusted preparation preconditions remain unchanged. No raw secret enters this service. Framework/JDBC/database logging and fatal JVM Errors remain outside this ordinary RuntimeException result boundary; no universal logging/privacy or live network-partition claim is made.

## Ownership and manager preconditions

The boundary has no Transactional annotation. It depends on the application's existing PlatformTransactionManager, JdbcTemplate/DataSource and proxied ProviderReceiptService. It starts one transaction with REQUIRED only after refusing ambient actual transaction, active synchronization or a bound resource for the expected DataSource. Never use REQUIRES_NEW, suspend, commit/rollback or clear a caller's transaction/resources. Ambient refusal returns UNAVAILABLE before invoking the manager or receipt body. Read/write entry points both obey this rule.

executePrepared starts a new READ_COMMITTED, writable transaction. lookupOwn starts a new REPEATABLE_READ, read-only transaction. Require non-null TransactionStatus.isNewTransaction, active synchronization/actual transaction, expected bound JDBC resource, actual JDBC isolation and Spring read-only flag before invoking the receipt proxy. Register a nonthrowing local completion-status recorder after a new status is established, as early as synchronization permits and before remaining fallible context checks/body invocation. If synchronization or registration is unavailable, no acknowledgement can be fabricated; owned cleanup is attempted once and the stated uncertainty rules apply. Manager/key adapters are not arbitrary untrusted plugins: the configured manager must honor normal Spring begin/completion cleanup and synchronous synchronization semantics. A begin failure must clean up its own resources; this boundary cannot repair a broken manager that throws after creating an unreported transaction. Do not dynamically detect a shared/foreign transaction and roll it back. If a returned status is not new, refuse without invoking the body or rolling back that unowned status. If a newly owned transaction fails context validation, attempt its rollback only, then report UNAVAILABLE if rollback acknowledgement/completion is confirmed, UNKNOWN for a write if termination is uncertain. Never publish a provisional result.

Completion is confirmed only by normal return from the owned manager operation, TransactionStatus.isCompleted and matching afterCompletion status recorded for that transaction. Do not infer commit from the receipt method returning, status flags alone, a callback alone or a possibly stale receipt query. The recorder is local state, not a durable ledger or extra transaction. Exceptions from commit/rollback are conservatively uncertain even if a callback reported a definite status. External manager resource cleanup remains its lifecycle responsibility.

## Write outcomes

executePrepared accepts exactly PR44's authenticated actor/org/key/typed command/prepared HMAC and fresh-only create-ID/prepared credential arguments. Invoke the proxied receipt execute exactly once. No generic caller callback, key dependency, external preparation or hidden receipt lookup is accepted. The existing proxy joins this owned transaction and freshly authorizes the actor. Preparation correlation remains a trusted-caller precondition; this boundary is not a cryptographic grant.

| Observation | Internal outcome |
| --- | --- |
| Ambient/unowned-context refusal or manager begin failure before body; newly owned invalid context with confirmed rollback | UNAVAILABLE, fixed COMMAND_UNAVAILABLE503, no result |
| Body returns, commit returns normally and completion is confirmed COMMITTED | COMMITTED with the exact receipt Result, no failure |
| Body throws a known ProviderReceiptFailure and owned rollback returns/finishes ROLLED_BACK | REJECTED with allowlisted fixed code/status, no result |
| Body throws another ordinary RuntimeException and rollback is confirmed | REJECTED with fixed COMMAND_UNAVAILABLE503, no result |
| Commit throws, regardless of callback/status; normal commit lacks confirmed COMMITTED; rollback throws/lacks confirmation after body or context failure | UNKNOWN with fixed COMMAND_OUTCOME_UNKNOWN503, no result |

Unknown commit may mean the DB committed, rolled back or cannot yet be established. Never retry commit, attempt another rollback after uncertain commit, reuse the command in a second transaction, look up a receipt automatically, change the idempotency key or delete/compensate external preparation. Return UNKNOWN without exposing nested failures, SQL, metadata, key identities or diagnostic messages. The caller may separately request lookupOwn after this method has returned and the manager has cleaned up. PREPARATION_REQUIRED is a normal known receipt failure only after confirmed rollback; future orchestration may then probe/prepare historically outside all transactions within its existing bounded protocol. A known rollback does not revoke or delete any previously committed matching receipt.

Allowlisted receipt codes/status are exactly UNAUTHORIZED401, FORBIDDEN403, INVALID_COMMAND400, INVALID_KEY400, INVALID_PREPARATION400, NOT_FOUND404, IDEMPOTENCY_CONFLICT409, REVISION_CONFLICT409, NO_CHANGE409, REVISION_EXHAUSTED409, CONNECTION_CONFLICT409, PREPARATION_REQUIRED409, RECEIPT_UNAVAILABLE500. A forged/unsupported code or wrong status from an internal ProviderReceiptFailure is not echoed: treat as ordinary unexpected failure. Use a fixed Code enum/status map; no arbitrary String/cause/Throwable is retained. Constructor/argument/configuration failures use fixed redacted failure or outcomes and never interpolate collaborator/input diagnostics. Fatal Error propagation is not ordinary-runtime acceptance.

## Explicit lookup outcomes

lookupOwn accepts actor/org/idempotency key only and calls proxied findOwn once in the newly owned read-only RR transaction. No HMAC key, secret preparation or alternate actor selector. FOUND carries the exact safe internal Receipt only after normal confirmed COMMITTED read completion. ABSENT has no receipt/failure and means absent in that authorized snapshot, not proof a concurrent/unknown command failed or cannot commit later. Only known lookup denial pairs UNAUTHORIZED401, FORBIDDEN403 and INVALID_KEY400 followed by confirmed rollback yield REJECTED with that fixed code/status. Corruption/storage failures (including RECEIPT_UNAVAILABLE), all other body failures, read begin/context/completion uncertainty yield UNAVAILABLE with LOOKUP_UNAVAILABLE503 and no receipt/partial null decision. In particular a found/absent body result followed by commit failure must be discarded. Never label a read uncertainty as a definite ABSENT or a fresh command grant.

All outcome/result/failure records are internal Jackson-ignore types with redacted toString and enforce state/payload combinations. Write states COMMITTED/REJECTED/UNKNOWN/UNAVAILABLE; lookup states FOUND/ABSENT/REJECTED/UNAVAILABLE. Only COMMITTED/FOUND carry results; only ABSENT has neither data nor failure. Failure contains a fixed enum and derived status, not Throwable/message/cause fields. No internal metadata/probe object is returned. Future public HTTP must use a separate exact allowlisted DTO mapper and complete its other prerequisites.

## Required acceptance evidence

Use real Spring receipt proxies, transaction manager, JDBC/Flyway H2 and native PostgreSQL. Fixed test-only manager decorators are dependencies of the manually constructed boundary only: receipt/connection proxies retain the original configured manager and participate normally. Fault interception must target the newly owned outer completion, never an inner REQUIRED participant. They may delegate an actual rollback then throw from commit, or delegate an actual commit then throw: both must return UNKNOWN, with zero automatic follow-up manager/body/key calls. Explicit healthy lookup afterward must observe ABSENT versus FOUND respectively. These are controlled completion-acknowledgement fault injections, not proof of a live dropped TCP commit acknowledgement. Body failures with acknowledged rollback are REJECTED and roll back parent/version/event/receipt and any test-only marker enlisted inside the owned body transaction; rollback acknowledgement failure yields UNKNOWN. Normal committed receipt is durable and can be recovered with fresh authority. Read completion failure after found/absent returns UNAVAILABLE, without exposing provisional data. Test afterCommit runtime failure and malformed/unknown afterCompletion reporting, missing/incompatible/new-status contexts and wrong manager resource, while preserving owner/resource boundaries.

Test ambient read/write transaction and synchronization/resource refusal without manager/body invocation or outer rollback-only mutation; outer caller can still complete its own marker. Test fresh authorization on explicit lookup, foreign/other-actor privacy, stale credential/role loss and malformed selected receipt failure mapping. Retain PR44's read-only snapshot absence semantics and zero network/key work. Inject dependency exception text containing sensitive sentinels; inspect every outcome field/toString and captured boundary logs for redaction, without claiming external Spring/driver/server logs universally safe. Verify exact calls and postconditions (no retry/automatic lookup/cleanup/delete), transaction state cleaned after supported manager faults, complete persisted row deltas and no changes to existing schema/migrations.

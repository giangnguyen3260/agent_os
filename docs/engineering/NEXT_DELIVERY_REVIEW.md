## Recommendation

Deliver **Edit draft task input** within the existing Task Detail workflow: a current organization ADMIN can review and save changes to an existing DRAFT task's title, description/input, acceptance criteria and priority. Persist a task configuration revision, protect against stale saves, and support durable same-command recovery. Remain on the existing task identity and return to its actual saved detail. No provider credentials, execution worker or simulated business values are needed.

This closes a practical gap: Add Task already collects and persists these fields, but a user who notices a mistake after saving cannot correct it. It develops the existing Overview / acceptance section rather than adding another inspection-only screen. This is a deliberately bounded portion of task configuration editing; owner and dependency editing remain future work. Do not describe it as completing all Task Detail or Figma functionality.

## Trigger and expected behavior

1. Current ADMIN opens an actual scoped DRAFT Task Detail and chooses **Edit draft input**. Read current saved configuration and edit eligibility, including an authoritative reason when blocked. MEMBER and non-DRAFT detail remain readable with an explanation for unavailable editing. Do not rely on a disabled button for server enforcement.
2. Load four actual values. Legacy null input/acceptance/priority appear blank and visibly need completion; never invent requirements or business text. Preserve owner and dependency display as read-only. Do not derive owner from pending resolver.
3. Validate title stripped 1–255, description stripped 1–8000, acceptance stripped 1–4000; priority exactly LOW/NORMAL/HIGH/URGENT, matching creation. Show inline errors and focus the first invalid field. Unknown/server-owned fields, string/boolean/fractional revisions and invalid enum/null required fields fail closed.
4. Review shows actual before/after differences and source revision. No-op review/save is blocked. Cancel, Back, route reuse and leaving dirty content follow existing discard-confirmation behavior. Keep unsaved private values in component memory only.
5. Save uses captured task revision, actor/scope and command identity. Revalidate authority and eligibility inside the transaction. A concurrent save or lifecycle/parent change produces a conflict; retain permitted local edits for explicit reload/review, never silently overwrite or issue a fresh command.
6. Confirmed save displays the persisted result; latest Task Detail reload shows the correction. Team/Mission task lists show the updated title where they already project it; summaries/status counts stay unchanged. Existing activity and Trace may show the safe task-linked configuration event, without private field values.
7. Network timeout, 5xx or malformed success is an unknown outcome. Freeze captured body/key; offer explicit receipt check or identical-command retry, with fresh authority. No automatic POST/PUT, new identity, guessed failure or duplicate audit. A receipt proves a historical save, not that current configuration still equals it.
8. On account/scope change, loss of access, destruction or stale callbacks, cancel requests and clear returned/private form and review data. Never replay captured private input after actor loss. Follow the Team Settings opaque recovery-locator precedent if retaining recovery information. GET failure after confirmed save retries GET only.

## Proposed API and persistence boundary

Implementation may refine naming while keeping these observable guarantees:

- `API_BOUNDARY.md` section 11 defines PATCH task metadata separately from assign/retry/review commands. Follow that metadata boundary using the current stricter Team-scoped task root `/api/v1/organizations/{org}/teams/{team}/missions/{mission}/tasks/{task}`: add member-readable `GET /configuration` with scoped current values, task-local revision and edit eligibility/reason; ADMIN `PATCH` task root with UUID Idempotency-Key and exact body `{expectedRevision,title,description,acceptanceCriteria,priority}`. This bounded PATCH requires all four editable fields for a reviewed replacement of that subset; it is not an arbitrary object merge. Eligibility must reflect current role and parent/task state, not a stored readiness override. No owner/dependency/status keys, execution command, or new legacy unscoped writer accepted.
- Configuration read includes nullable legacy values. First save must supply the four valid values. Existing Task Detail wire can remain unchanged by keeping revision in the new configuration read; production validators for the new response must bind every scoped identity and typed field. Avoid silently breaking Task Create's stored original-response receipts by changing its DTO.
- Add ADMIN `GET /configuration/receipts/{key}` under the same scoped task root for explicit recovery, restricted to the authenticated command actor. Return a validated historical receipt or a documented not-found response; absence is not proof that an outstanding write failed. Fresh authorization applies; no GET performs a mutation. Successful PATCH/receipt envelopes bind organization/Team/Mission/task, accepted revision and actual saved configuration; the UI must distinguish historical confirmation from a fresh current read.
- Add a bounded nonnegative task configuration revision (legacy/default 0), durable edit receipts scoped to organization/account/task/key and immutable task configuration history recording accepted revision, authenticated actor, timestamp and actual configuration snapshot. Preserve the pre-edit snapshot when first editing a legacy task, without inventing original-author provenance. Configuration history is private business data, not public audit payload or execution input/output history; no new history screen is required. Adopt a strict integer range with an explicit overflow rejection; timestamps alone are insufficient concurrency tokens. Preserve existing rows, dependency constraints and creation receipts; no business fixtures in migrations.
- Authorization lock order follows organization → account → membership, then Team → Mission → Task. Reuse the existing helper boundary and recheck current scoped state under locks. Parent locks must serialize with task creation and future intake controls; any future lifecycle writer must share the Task lock/revision discipline. No network/provider operations under locks.
- After fresh authorization and scoped identity checks, look up command receipt before mutable status/revision/parent eligibility checks. Same key plus canonical same body/scope returns original success, including after a later configuration/state change. Same key plus different body returns IDEMPOTENCY_CONFLICT. A new command requires current eligibility and expected revision.
- Atomically update only the four fields, updated timestamp and task revision; insert immutable configuration history, original-response receipt and one task+Mission-linked HUMAN audit event. Actor identity comes from authentication. Audit payload contains only safe revision metadata, never title/input/acceptance, owner data or request bodies. No-op commands produce no revision/history/audit/receipt. Any failure rolls back all effects.
- Return 200 for first update and replay. Validation 400; unauthorized/foreign organization follows existing 401/403 transport; absent or mismatched parent/task 404; stale revision 409 TASK_CONFIGURATION_CONFLICT; ineligible lifecycle/parent 409 TASK_NOT_EDITABLE; reused-key mismatch 409 IDEMPOTENCY_CONFLICT. Freeze these new codes in the delivery contract. Preserve existing closed `/error` behavior rather than broad security refactoring.

## Remaining lifecycle and runtime blockers

Draft correction is implementable with ordinary application/database tooling. It does not depend on production provider credentials. Broader runtime functionality still needs authoritative plan/task-graph versioning and transition orchestration; executable model/tool authorization and revocation checks; real provider/worker integration; run/attempt/input/output snapshots and artifacts; retry/review/cancel semantics, limits and cost accounting. Requested configuration and stored status must not substitute for those sources.

Pause/resume intake remains an honest subsequent mutation, provided its contract serializes flag/version changes with creation and this proposed edit gate. Mission execution pause/cancel remain separate lifecycle work. Dependency editing requires graph validation beyond immutable new-task edges. Owner editing requires eligibility and reassignment rules. Approval/View run/Retry task cannot be enabled merely because an audit record or a human approval grant exists; linkage, authority and execution effects must first be authoritative.

The next slice is complete when a real authorized user can correct persisted draft input, resolve a genuine concurrent-save conflict and recover an ambiguous committed save through the existing screen flow. Production execution readiness, new permission policy and complete Figma coverage remain separate outcomes.

### Concrete acceptance blockers and implementation checks

No contract-level blocker requires BE/FE to stop. The following are specific closure gates; failure of any is a blocker, not a newly requested policy decision:

1. **Replay ordering:** a committed same-key command must return its original receipt before checking current snapshot/no-op/blockers. Test replay after another edit, intake pause, non-DRAFT transition and revision exhaustion; also test revoked ADMIN denial. Interpret the contract's “changed key body conflicts” as **same key with different canonical body**. A new key is not inherently a conflict; it follows ordinary current-snapshot, eligibility and no-op checks.
2. **Snapshot identity:** freeze one domain-versioned canonical fingerprint encoding in backend code, including deterministic dependency ordering, null/text/timestamp treatment and every listed snapshot field. FE treats the fingerprint as opaque. Native tests must independently mutate owner, dependencies, updated_at and parent intake state/version without changing edit revision, then prove stale preflight/commands cannot commit. Do not omit an unchanged-by-this-command field from the fingerprint because it is read-only in this form.
3. **Receipt correlation:** Receipt has no key field. Validate its exact shape, scope, revision and before/after values; bind it to the captured request key through the specific POST/receipt-GET request and actor/scope/generation fences. Do not add an undocumented response key or accept a late response from a different recovery locator. GET null is not proof of failed commit; an identical retry can still recover it.
4. **Unknown versus definite conflict:** malformed/lost success stays UNKNOWN with the exact captured key/body; only explicit same-command retry writes. A definitive conflict permits fresh context/review, never an automatic replacement command. History/event/audit/receipt failures must roll back fields and revision together; no-op rejection and successful replay must leave all business tables unchanged.
5. **Wire and UI parity:** enforce code-point lengths and forbidden-control/surrogate rules from the frozen contract rather than copying older creation validators unchanged. Review shows real nullable before values and complete desired values; priority starts blank for missing legacy data. Held-response and focus/visibility tests must prove neither stale context nor stale save success can restore private UI after authority/identity loss.

Existing implementation tooling, real PostgreSQL concurrency/rollback probes, backend/frontend checks and real-backend responsive browser evidence remain required. No provider credential or runtime integration blocks this draft-edit slice. Typed missing-input/source/blocker reevaluation, dispatch suspension and execution artifacts remain the concrete blockers for the wider Figma lifecycle actions, not dependencies to fabricate for this delivery.

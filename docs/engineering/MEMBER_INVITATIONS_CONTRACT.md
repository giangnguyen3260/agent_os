## Bounded policy

Fresh enabled credential-version-matching organization ADMIN creates/resends/revokes invitations in that organization. Invite grants organization MEMBER only, no Team/Agent membership, ADMIN, approval grant, tool/model authorization or runtime effect. A later separate role-management command may promote an accepted member. Existing membership, including ADMIN, is preserved without role change. Rejoining may make a separately retained still-eligible approval grant usable again under existing checks; no grant is created/reactivated by this writer. Admin and public acceptance review must disclose this generic consequence: “Quyền duyệt riêng còn hạn có thể tiếp tục có hiệu lực khi tham gia lại.” No public signup or first-Admin bootstrap; new account creation requires a valid invitation capability.

Email: Java strip + lowercase Locale.ROOT, ASCII dot-atom mailbox, max254 chars and local part1..64 chars, no whitespace/control/CRLF, one @. Local characters are ASCII letters/digits and !#$%&' *+/=?^_`{|}~.- with the literal space excluded; no leading/trailing/consecutive dot. Reject comma, semicolon, colon, quotes, backslash, angle/square brackets and all address-list/display-name syntax. Domain requires a dot, labels1..63 ASCII letters/digits/internalhyphen with no edgehyphen. This is a deliberately bounded mailbox grammar, not all RFC email syntax. Display name: Java strip,1..255 Unicode code points, no C0/DEL or isolated UTF16 surrogates. New password: no trim,14+code points, max72 UTF8 bytes, no isolated surrogates; BCrypt12 through existing PasswordEncoder. Existing accounts MUST authenticate exact normalized recipient email, enabled/version-current; invitation cannot reset/change existing credentials, displayName, sessions or other-org membership. Disabled accounts cannot accept or be recreated.

Fixed invitation lifetime72h from original creation, not extended by resend. Resend cooldown60s from last queue request, max5 SMTP attempts per job with configured retry delay. All configurable runtime values must be bounded and documented. One live pending invitation per org/email enforced under org mutex; expired/terminal invitations permit a fresh separate creation. Status EXPIRED is derived from PENDING plus expiresAt <= current time, never fabricated acceptance. Idempotent replay may return a historical queued/revoked receipt and does not imply current state or email delivery.

Feature disabled by default outside explicit local Compose/CI configuration. Delivery uses real SMTP to the isolated Mailpit inbox in development, never tools sending external mail. Only an explicitly configured trusted HTTPS frontend URL (loopback HTTP allowed) supplies links; ignore Host headers. Never return a raw link/token in API, audit or logs.32 random token bytes, URL-safe43 chars; only SHA256 digest in DB. Durable mail jobs store invitation reference/generation/state, no raw token or message. Worker generates token only in memory, installs new digest only when SMTP acknowledges and transaction commits. Failed replacement preserves prior delivered digest; resend does not immediately invalidate that prior link or extend expiry. SMTP acknowledgment is not exactly-once or actual human receipt. Acceptance/revoke cancels pending jobs; crash before commit can leave an emailed invalid token, never a reused accepted capability.

The latest create/resend issuer ID plus credential-version snapshot must still be an enabled current ADMIN at dispatch/inspect/accept. Otherwise no delivery/redemption. Another current ADMIN may explicitly resend, rebinding issuer authority to that actor while retaining fixed expiry and preserving old delivered digest until replacement ACK. This is deliberate reauthorization of that pending invitation, including its still-delivered capability. Revoke remains available to fresh ADMIN independent of original issuer. No automatic invitation-wide side effect is added to role changes.

## Persistence/locking

V015 additive tables: organization_invitations; invitation_mail_jobs; invitation_events; invitation_receipts; invitation_email_locks (email digest only). No production seed. Invite/event/receipt retained independent of live recipient membership. Index list/history, token digest unique when nonnull, org/email eligibility lookup, mail pending availability. Enforce enum/bounds/key/FK consistency in schema and service. No destructive migration or existing-ledger reset.

Administrative writes: organization mutex FIRST (same protocol as role/grant writers), then acting human + membership locks, then scoped invitation (for create live email check under org). Scope before private target metadata, fresh issuer checks after waits. Reads ADMIN-only service fresh authority under read-onlyREPEATABLE_READ; writesREAD_COMMITTED. Replay actor-only branch cannot fall into a second lock-order path.

Acceptance: digest lookup proves candidate org/invitation, lock organization, then global invitation_email_locks digest BEFORE ANY human lock. All invitation account creators share that email mutex across orgs. Resolve existing recipient after email lock, acquire distinct existing issuer/recipient human locks in lexical unsigned UUID string order, then corresponding existing scoped memberships in same order, invitation row and role ledger. Recheck token/time/issuer/current actor after waits. New globally unique human insert never overwrites an existing email; concurrent unsupported bootstrap/other creator unique-email conflict rolls transaction back to409, requires fresh inspect/sign-in. No old account is silently converted into signup. No writer may acquire email mutex after holding a human row.

Adding membership: missing member_role_ledgers -> revision1; retained row -> existingrevision+1, maxoverflow409. Never reset retained revision or invent a before-role for a join; restricted invitation event records membership creation and new role revision. Existing role events remain readable unchanged (revision gaps allowed). Historical role commands from before a removed/rejoined membership must conflict. Approval grants, sessions/credentials of existing humans, Agent/Team/Mission/Task/runtime rows remain unchanged.

Dispatch must lock organization then issuer human/membership then invitation/job in a consistent order (no email mutex/recipient locks). No human-first organization wait. Recheck latest generation, pending/unexpired state and issuer before sending; cancelled/expired/ineligible jobs becomeCANCELLED/FAILED safely, no new usable digest. Bound batches/timeouts; SKIP LOCKED selection must not invert lock order. Never log SMTP body/token. Privacy and rollback tests cover safe-audit failure and DB lock waits; H2 tests do not establish PostgreSQL races.

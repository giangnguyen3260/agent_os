## Trust model and limits

A specifically configured external worker is allowed to attest that it actually performed the exact external secret-version and historical HMAC verification described below. PostgreSQL authenticates the worker, binds its assertion to captured immutable database metadata and applies race/time/state rules. SQL cannot prove a network check happened, establish the worker's honesty or validate secret bytes it never receives. A compromised authorized producer can lie about its permitted assertions. That is an explicit trust assumption, not an unresolved claim that role membership supplies cryptographic proof.

No observer adapter is delivered by this slice. Production USABLE/VERIFIED assertions require separately reviewed worker wiring, secret/key permissions, typed verification outcomes, bounded deadlines and operational ownership. A connectivity ping, cached status, current-key lookup or syntactically valid public `CredentialBoundary.Metadata` is insufficient. Credentials, recoverable encodings and external responses never enter evidence SQL.

Prepared provenance means a durable, authenticated **producer assertion** about exact preparation, not a signature or independently verifiable proof. Only a registered producer with the `PREPARE` permission may submit that assertion; a general health publisher, HTTP login or caller possessing Metadata may not mark it verified. Record that provenance explicitly. The existing public Metadata constructor and generic `CredentialBoundary.Failure` are not trusted preparation or mismatch producers. Do not add a public `verified=true` parameter to either.

## Original-login registration and fence authority

Extend the private registry with operator-controlled identity and authorization records; V025's `(publisher_id,publisher_epoch,publisher_fence)` alone is not authentication. Keep health's lack of a registry FK so old observations cannot block invalidation.

Registration records contain the publisher ID, authenticated LOGIN role name and role OID, one exact organization UUID, enabled flag, allowed assertion kinds (`HEALTH`, `PREPARE`, `INTEGRITY_FAILURE`) and explicit provider scope allowlist. No wildcard permission by omission. All are nonsecret private metadata. Resolve one exact publisher/LOGIN/organization binding per attempt; a LOGIN used for several explicitly registered organizations gains no cross-organization authority. Enforce uniqueness of each publisher registration; reject missing, duplicate, disabled or inconsistent registration. Role rename/recreation or OID/name mismatch requires operator re-registration and fencing; never silently follow a reused role name. Record both identity values in provenance.

Inside SECURITY DEFINER, resolve `SESSION_USER` to its catalog role and compare that original login's name/OID to registration. `CURRENT_USER` is the function owner and is not caller identity. Never authorize using payload publisher ID, custom GUC, application username, `SET ROLE`, `current_role` or membership alone. A requested publisher ID, if accepted at all, is only an equality check against this resolved registration. Ordinary worker logins cannot SET SESSION AUTHORIZATION to another login; privileged sessions able to do so are outside this boundary and must never be used as workers. Connection pooling must preserve the real authenticated LOGIN; one shared administrator with per-request SET ROLE is prohibited.

The operator registers a new publisher with positive int64 epoch and fresh unique UUID fence. Replacement, restore, compromised worker, identity/scope/kind change, disable/re-enable and ownership handover must invalidate outstanding attempts: lock the registry row, require its expected current epoch/fence, increment epoch without overflow and replace fence with a fresh unique UUID. Runtime callers cannot advance/reset/register it. On epoch exhaustion, disable and provision a new publisher ID; never wrap or reset. Disabling must fence atomically, not merely hide membership. Restored evidence is not trusted until an explicit operator fence step completes before workers/readers are admitted; do not reset timestamps or replay restored tickets. Provisioning refusal/verification is safer than automatic privilege repair.

## Operator-installed storage and callable surface

Implement these tables through the operator installer, not a Flyway migration. Implement private tables in `agentos_evidence_private`; keep the V025 evidence tables in `public` and reference them fully qualified. All new storage has exact catalog/value allowlists, no credential/ciphertext columns, and no public serialization. Required additional records are:

- Registration and scope/kind grants as above, joined to the V025 registry triple.
- Immutable attempt records: random opaque attempt UUID, kind, original-login name/OID, publisher triple, exact eight-field V025 binding, captured verifier (or an internal immutable binding to that exact version row), relevant captured evidence revisions/absence, DB start time, deadline and consumed state. A token is an attempt handle, not a bearer authority. No runtime SELECT or DML on these tables.
- Immutable integrity-producer assertions: assertion UUID/kind, attempt ID, exact version/binding, original-login name/OID, publisher triple, DB capture/accept times, fixed outcome and fixed protocol version. A private keyed provenance relation binds the V025 integrity identity/publication revision to its assertion; no V025 column changes. Exactly one matching provenance record per accepted integrity revision; never infer provenance from an unlinked audit row. No arbitrary free text, raw exceptions, credentials, verifier duplication in logs or provider response bodies. This is required integrity provenance, not a health command receipt ledger; do not add unbounded health publication history for readback. Operational attempts have the numeric capacity and cleanup rules below; required integrity provenance is retained separately and cannot be erased by operational cleanup.

Define the SQL callable API below. `scope` expands to organization UUID, connection UUID, provider and credential revision; `binding` is the complete eight-column tuple from V025. Use explicit scalar PostgreSQL parameter/return types in the implementation, not JSON payloads or caller-controlled composite type names. UUID, bigint, timestamptz(6), constrained fixed enums/text and boolean presence tags suffice. No function accepts a caller-selected recorded_at, observed_at, published_at, trusted identity, next revision or verified flag.

| Function | Parameters and result | Permission |
|---|---|---|
| `begin_health` | Exact scope; returns attempt UUID, exact stored binding/verifier needed by the worker, DB observed_at and fixed deadline. Captures current health CAS internally. | HEALTH |
| `publish_health` | Attempt UUID, outcome USABLE or UNAVAILABLE, `component_deadline_present boolean` and `component_deadline timestamptz(6)`; returns fixed ACCEPTED or REJECTED. | HEALTH |
| `begin_preparation_assertion` | Exact active scope; captures immutable version and integrity CAS; returns attempt UUID and exact stored metadata for comparison with the worker's own preparation result. | PREPARE |
| `assert_prepared` | Attempt UUID; submits the fixed PREPARED_VERIFIED assertion, never a general status argument; returns ACCEPTED or REJECTED. | PREPARE |
| `begin_integrity_verification` | Exact retained scope; returns attempt UUID and exact immutable metadata, capturing integrity CAS. May target a historical version. | INTEGRITY_FAILURE |
| `publish_integrity_failure` | Attempt UUID; fixed CONFIRMED_MISMATCH assertion only; returns ACCEPTED, ALREADY_FAILED or REJECTED. | INTEGRITY_FAILURE |

`publish_health` requires both deadline parameters explicitly; there are no argument defaults or implicit presence inference. The only absent representation is `(false, NULL)`. The present representation is `(true, a finite timestamp)`. A NULL presence boolean, false with a non-NULL timestamp, true with NULL, or true with a nonfinite timestamp returns REJECTED/ATTEMPT at argument validation. Do not coerce, ignore or normalize mismatched pairs. For a valid present pair, civil-range/expiry/ordering checks occur later at TIME precedence; an expired finite component deadline returns REJECTED/TIME. Absence uses the captured deadline; presence uses the earlier of the component and captured deadlines, so a later component deadline cannot extend validity.

Only these six reviewed entry points receive publisher EXECUTE. Each independently authenticates registration, kind and scope; permission on the group never substitutes for those checks. No generic SQL writer, arbitrary-integrity-state function, clear/repair, delete, backfill-verification or runtime registration API. No privilege to change credential versions is required by these routines. Use private helpers only; document every exact signature/grant in the implementing operator script and test it.

## Attempt capacity and operator cleanup — F7 pending QC decision

BA/SA proposed freeze for QC consensus: at most **4096 unpinned operational attempt rows per organization**, aggregated across every publisher, LOGIN, provider, assertion kind and state. This is a total row cap, not just an in-flight or unexpired cap. Consumed, rejected-but-retained and expired unpinned attempts count until operator cleanup actually removes them. New organizations receive no exemption; creating another publisher or fencing does not reset the count. This bound is a proposed source-review disposition, not a claim of QC agreement or executed capacity tests.

Every begin_* function holds the existing organization-row mutex, validates authority/binding/capture time, then counts the organization's unpinned attempts before insertion. At count >=4096, return fixed `REJECTED / CAPACITY` with no token, row, counter or timestamp change. Do not evict or sweep to make room, reserve slots outside the transaction, or infer success after count/commit uncertainty. Concurrent captures for the last slot serialize on this mutex: at most one inserts. The same mutex protects transitions from unpinned to pinned; successful publication otherwise keeps its attempt counted until cleanup. No per-worker counter can bypass the organization-wide limit.

An attempt becomes pinned only atomically with an accepted integrity transition and its exact immutable provenance linkage. HEALTH attempts and unsuccessful assertions never become pinned. Pinned attempts are excluded from the 4096 operational cap but cannot become an arbitrary command ledger: this protocol permits at most **two pinned attempts and two transition assertions per immutable credential version** (absent→VERIFIED_AT_WRITE→FAILED), or one for absent→FAILED. Existing VERIFIED rejection and ALREADY_FAILED no-op add none. Enforce unique exact version/publication-revision provenance and one producer assertion per accepted transition; no runtime alternative transition can grow that bound. Total pinned retention scales with retained immutable credential-version history; no claim of a fixed global history-size cap is made. Deletion/retention of that history is outside this slice.

Cleanup is an explicit operator action, with no publisher EXECUTE/DML grant and no background/default sweep. It may delete only unpinned operational attempts when the post-lock DB clock is **at or after captured deadline + five minutes**; expiry alone or consumption alone is insufficient. Use checked finite arithmetic and refuse candidates whose eligibility cannot be represented. Recheck eligibility and absence of any integrity provenance reference while holding the same organization mutex and attempt-row lock. Foreign keys must prevent deletion of referenced/pinned attempts; never cascade into provenance or evidence. A capture/publication/cleanup race therefore cannot remove an attempt just pinned by a committed integrity transition. Lock order remains the prescribed organization-first order; cleanup never takes publisher first and organization later.

The operator explicitly selects the organization and a bounded batch of at most4096 eligible attempts, ordered by deadline then attempt UUID; no arbitrary cross-organization or history sweep. Cleanup only removes eligible operational rows. It cannot edit evidence, identity registrations, epochs, provenance, pinned state, revision counters or timestamps, and is not a way to infer an uncertain command outcome. If capacity remains exhausted, begin_* continues to return CAPACITY; no automatic successful retry, grace shortening or cap increase. A later capture after authorized cleanup is a new independent attempt and check.

## Transactions, capture and health publication

All worker operations use real authenticated sessions and short READ COMMITTED transactions on the intended database. Reject unexpected weaker/different isolation or read-only contexts. Functions do not commit: the worker must commit each capture before starting external work and commit publication before reporting acceptance. A returned row before commit is provisional. No network/key operation while any capture/publication transaction or business lock is held. Completion uncertainty is failure to claim publication; do not restamp/retry an old assertion as a fresh check.

Capture locks may be short, but preserve existing business order: organization-row mutex first; scoped connection-row lock; SELECT-only read of the exact immutable credential version; publisher registry/registration with a shared lock; integrity; health; private attempt. These internal publisher functions do not impersonate human authority or take policy/account/membership locks. Acquire the shared publisher/registration lock before integrity/health and hold it through commit so operator fence updates conflict and serialize. Registry-only operator fencing never subsequently takes business locks. Every entry point and integration path must follow this order; inspect rotation and future preparation writers for inversion. Serialize absent evidence through the locked organization/connection parent, not a credential-version lock or SELECT FOR UPDATE on a nonexistent evidence row. Re-read registration/fence while locked; do not rely on a pre-lock membership check.

Version locking clarification (F1): `public.provider_credential_versions` is SELECT-only for the definer owner as well as read-only for supported runtime readers; none of these functions uses FOR UPDATE, FOR SHARE or FOR KEY SHARE on that table. PostgreSQL row-locking SELECT requires UPDATE privilege on at least one column, so a locking SELECT must not be smuggled into this SELECT-only design. No version-column UPDATE grant is authorized, including to the definer owner. Under the locked connection parent, read and revalidate the entire exact version binding and verifier for every capture/publication, including retired-version failure. Safety relies on Q3's effective prohibition of supported runtime version mutation; privileged operator corruption remains outside this guarantee. Registry/registration shared locks and organization/connection locks still need their actual PostgreSQL locking privileges: grant the trusted definer owner only the necessary explicit column UPDATE privileges there, never to caller LOGINs or the publisher group, and list them in the grant manifest. Functions never use those grants to mutate business metadata. Test actual execution with the owner's version UPDATE privileges absent.

`begin_health` revalidates the parent active revision under its parent lock and reads the complete immutable version metadata with plain SELECT, captures health publication revision with an explicit ABSENT tag, and captures the current publisher triple. Sample `pg_catalog.clock_timestamp()` at microsecond precision after all capture waits, immediately before creating the attempt. This is the original DB check-start bound: it precedes all external checks, and any commit/scheduling delay consumes its TTL. Persist `observed_at` and `deadline = observed_at + interval '60 seconds'` with checked finite civil-range arithmetic. The worker exposes the capture to its check routine only after capture commit; an uncommitted/rolled-back attempt cannot be used. Never substitute transaction-start current_timestamp, client/JVM clock or publication time.

The worker starts a new actual independent check after capture commit. It uses the exact external immutable version, exact scoped reference, recorded historical HMAC key and domain, and verifies the scoped credential binding before declaring USABLE. No current-key fallback, successful service ping, cached result or provider request. Separate component checks share this earliest DB start bound; any earlier component expiry can only shorten validity. An expired attempt requires a new capture **and new checks**. The SQL handle binds an assertion to a worker; it does not prove these worker behaviors.

`publish_health` executes this atomic algorithm:

1. Resolve original LOGIN and registration, locate the attempt without trusting caller metadata, and lock the business/evidence/registration/attempt rows in the order above. Recheck the locked attempt, unconsumed state, owner identity, HEALTH permission and current exact publisher triple.
2. Revalidate organization/connection/provider, active credential revision and every exact version field, including verifier immutability and all reference/key/domain fields. Parent rename/enable does not invalidate otherwise exact credentials; rotation does. Absence of a dependency or malformed binding is rejection, never a replacement/default row.
3. Take a fresh microsecond PostgreSQL wall clock **after all lock waits**, before any health CAS or sticky-state decision. Compute valid_until from the validated deadline pair: captured deadline if absent, otherwise the earlier of captured deadline and component deadline. All times must be finite and in V025's civil range. Require `observed_at <= published_at < valid_until <= observed_at + 60s`. When prior health exists, also require `published_at >= previous published_at` and `observed_at > previous observed_at`. Complete every TIME check, including prior-health ordering, before sticky FAILED, CAS or increment checks. Reject equal/older observations, a future captured start, expired deadline, backward clock ordering and excessive validity as REJECTED/TIME. Equality at expiry is expired. Do not clamp into success or extend TTL after a wait. Use the captured checked deadline rather than unchecked timestamp addition; an unrepresentable arithmetic operation returns REJECTED/EXHAUSTED without a write.
4. Check sticky integrity first: if integrity is FAILED and the requested outcome is USABLE, return REJECTED/INTEGRITY_FAILED. For an allowed outcome, compare current health revision/absence to the captured CAS. Absence is distinct from revision zero. First insertion requires continued absence; otherwise require exact equality. CAS/absence loss or a nonpositive stored revision returns REJECTED/CONFLICT. Only after CAS succeeds check increment capacity: max-int64 returns REJECTED/EXHAUSTED. Accepted insertion starts at 1; accepted update increments exactly once. Thus the health decision order is TIME (including previous-health ordering), sticky FAILED, CAS, then increment/MAX. UNAVAILABLE follows the same order but does not reject merely because integrity is FAILED.
5. Do not derive integrity verification from either health outcome. Write health with the captured binding/triple, post-lock published_at and checked next revision; consume the attempt in the same transaction. No health write can clear or replace integrity.
6. Commit before acknowledging ACCEPTED. Rejection changes no evidence, provenance, counter, timestamp, expiry or consumed flag. The caller discards a rejected attempt and performs a fresh independent observation if needed; it may not reattach its cached outcome to a new attempt. Replayed successful tokens reject. Do not perform conflict-upsert without the full locked CAS/state checks.

Both outcomes require the same capture, time, identity and fence checks. UNAVAILABLE is affirmative bounded evidence of an observed problem; missing/expired evidence remains unavailable without a cleanup job. This protocol provides no successful default.

## Exact results, CAS/MAX and completion uncertainty

Every mutation entry point returns a fixed status and reason, plus a private exact candidate descriptor only on ACCEPTED. The descriptor is the scoped evidence identity, complete binding, publisher triple, assertion kind, accepted revision, fixed state and exact stored timestamps; it contains no credential or diagnostic. Capture returns that attempt's private allowlisted fields, or the same rejection envelope with no data. `ALREADY_FAILED` is permitted only for publish_integrity_failure and returns no new publication descriptor. These SQL return values remain provisional until commit acknowledgement.

| Status | Reason | Meaning and mutation |
|---|---|---|
| ACCEPTED | NONE | Guarded write and attempt consumption staged atomically; worker reports accepted only after known successful commit. |
| ALREADY_FAILED | NONE | Exact-version integrity already FAILED; no row, counter, provenance, timestamp or attempt change, including at max revision. This confirms the existing sticky state in this transaction, not that this command previously committed. |
| REJECTED | AUTHORITY | Missing/disabled/wrong LOGIN/OID/kind/org/provider registration or changed epoch/fence. No mutation. |
| REJECTED | ATTEMPT | Missing, consumed, wrong-kind or wrong-identity attempt, invalid scalar argument, or invalid component-deadline presence/value pair. No mutation. Do not expose which condition. |
| REJECTED | BINDING | Missing/changed/malformed version or scope, or retired target for health/prepared success. No mutation. |
| REJECTED | CONFLICT | Health CAS/absence loss; preparation integrity already exists; or impossible captured-integrity revision ahead of current state. No mutation. |
| REJECTED | TIME | Nonfinite/future/expired/reversed/equal-or-stale observation, regressing publication clock, or invalid deadline. No mutation. |
| REJECTED | CAPACITY | Proposed F7 reason, pending QC decision: begin_* would exceed 4096 unpinned attempts for its organization. No mutation, token or automatic cleanup. |
| REJECTED | EXHAUSTED | Increment or timestamp arithmetic cannot be represented safely. No mutation, fixed operational alert; never wrap. |
| REJECTED | INTEGRITY_FAILED | Health USABLE or preparation success attempted against FAILED. No mutation. |

Use authority, attempt, binding, time, then locked state/CAS/increment validation as the fixed precedence; time checks include ordering against previous health before CAS. Within health state validation, the exact order is sticky FAILED, CAS/absence/revision validity, then increment/MAX; none precedes TIME. A TIME violation therefore wins over simultaneous FAILED, CAS loss or MAX, and INTEGRITY_FAILED wins over simultaneous CAS loss or MAX for USABLE. Thus already-FAILED remains FAILED even at MAX; USABLE cannot rewrite it. Unknown enum/null/oversized scalar values map to REJECTED/ATTEMPT when the function can validate them. PostgreSQL protocol/type errors before entry are handled as safe failures below, never raw diagnostics. A private typed enum must not leak its parser error to application output. For begin_* only, CAPACITY is checked after authority/attempt-argument/binding/time validation and before insertion; it never changes publication validation precedence.

Preparation and failure precedence (F2): both start with AUTHORITY → ATTEMPT/argument validation → BINDING → post-lock TIME, before any integrity state/CAS/MAX decision. `assert_prepared` then checks FAILED → REJECTED/INTEGRITY_FAILED; otherwise existing VERIFIED or captured/current absence/revision inconsistency → REJECTED/CONFLICT; only absent integrity with captured absence creates revision1 and provenance. No increment of an existing VERIFIED row is supported. `publish_integrity_failure` then checks existing FAILED → ALREADY_FAILED, including at MAX; otherwise checks captured/current integrity consistency → REJECTED/CONFLICT where impossible; otherwise performs the failure-dominant transition using the locked current revision, checking MAX → REJECTED/EXHAUSTED before increment. For both, TIME wins over simultaneous FAILED, CONFLICT or MAX. For failure, ALREADY_FAILED precedes consistency/increment checks once identity, attempt, exact binding and TIME are valid. A newer valid VERIFIED revision is not a consistency error; the exception to captured equality is intentional. These are the same state orders used below, not a second competing algorithm.

For confirmed failure only, captured integrity absence or an older captured revision does **not** require equality with the locked current revision. If current integrity is VERIFIED, use that current revision for checked CAS to FAILED. A newer health revision is irrelevant. If current integrity is absent, insert FAILED at 1. If current state is FAILED, return ALREADY_FAILED without increment. For a non-FAILED current state, a captured revision greater than current, or disappearance of a previously captured integrity row, is corruption/conflict and rejects. At MAX with VERIFIED, return REJECTED/EXHAUSTED and preserve VERIFIED: do not claim FAILED was recorded or bypass the bound. Raise a fixed operational alert, suppress any worker success claim and require operator investigation; this contract does not claim that rejected failure instantly revokes an already published health row. Existing health still expires on its original <=60s bound. At MAX with FAILED, retain ALREADY_FAILED. No MAX/CAS path clears FAILED, rewinds revisions or modifies a replacement version.

Known server-reported rollback (including deadlock, timeout, serialization/dependency/permission failure) maps at the worker boundary to `FAILED / DEPENDENCY_UNAVAILABLE` with no SQLSTATE, SQL text, bind values or cause. A connection loss or commit acknowledgement loss where completion cannot be established maps to `UNKNOWN / COMPLETION_UNKNOWN`. Do not infer rollback from transport loss. These are worker results, not extra successful SQL statuses. No automatic retries for either result.

V025 stores the latest health row and overwrites earlier publications; there are no command receipts. A separately authorized private/operator readback may confirm that a **known exact candidate descriptor** currently matches every identity/binding/publisher/revision/state/timestamp field, with linked integrity provenance where applicable. It cannot confirm an older command's absence, rejection or success once a newer row replaced it. A mismatch, missing row, lost candidate descriptor, later publication, or unreadable/uncertain readback remains UNKNOWN. Consumed capture state is not a transaction receipt API. Never claim a read of latest state resolves historical completion. Do not add a general read/recovery EXECUTE grant to the six-function publisher surface for convenience. Future immutable publication receipts would require an explicit separately scoped schema, bounded retention and acceptance tests; none are required/delivered here. Recovery proceeds with a next independent capture and verification, never automatic replay or restamping of the old result.

## Prepared provenance and sticky integrity

`begin_preparation_assertion` is for a registered producer's own fresh preparation, after the exact version is durably stored and active. Preparation/secret storage occurred outside business transactions. The producer must compare its own successful prepared result to the captured complete metadata and attest that its trusted path performed scoped HMAC preparation and exact external-version verification. A fresh independent exact-version read/verification may establish the assertion only through that explicitly reviewed producer policy; merely reading an old Metadata row may not. No bulk historical adoption or migration backfill is authorized. If the producer cannot tie the assertion to its own preparation or permitted verification, it must not call assert_prepared.

`assert_prepared` uses the identity, parent-lock/SELECT-only-version, fence, immutable binding and active-version checks and captured integrity revision/absence CAS in the exact F2 precedence above. Require a fresh attempt within its original at-most-60-second deadline using a post-lock DB clock; no future/nonfinite/reversed time or overflow. Create VERIFIED_AT_WRITE only from absent integrity, with revision 1 and linked PREPARED_VERIFIED provenance in the same commit. Reject existing VERIFIED or FAILED rather than refresh/relabel/replay them. Do not clear failure or reuse an assertion for another binding. Delayed preparation for N cannot mark N+1 verified. Until this separate assertion commits, even a successfully stored active credential remains unavailable. This bounded SQL slice intentionally does not claim atomic external preparation/business rotation; a future atomic integration requires its own reviewed boundary. Failures/orphans never manufacture VERIFIED evidence.

`publish_integrity_failure` accepts only a trusted worker's typed confirmed mismatch after verification against the captured exact retained version. Key/read timeout, missing key, external service outage, parser failure and consumer callback exception are not confirmed mismatches. Existing generic Failure must not be translated wholesale into FAILED. No consumer executes before verification. Record only fixed CONFIRMED_MISMATCH provenance, never the secret or raw failure reason.

Lock the organization/connection parent, read the exact historical version with plain SELECT, and validate its complete binding/verifier and current worker epoch even if the parent now points to N+1. This is the sole active-version exception: write FAILED against N only; never mutate N+1, the parent's revision or another version's health. A same-version verified success cannot supersede it. Acquire integrity locks in the prescribed lock order before the post-lock clock and validation. After the F2 authority/attempt/binding/TIME and sticky-state checks, for absent/VERIFIED integrity, use the already locked current state and CAS that current revision when writing FAILED; do not acquire a new lock after sampling the validation clock. The captured revision is checked for consistency but a newer VERIFIED revision or health revision is **not** a reason to discard a confirmed exact-version failure: promote the locked same-version state to FAILED with checked next revision. Existing FAILED is a fixed ALREADY_FAILED no-op; no revision/recorded_at refresh. Document this additional fixed return value for this function only. Revision exhaustion rejects with no mutation and raises a fixed operational alert; never wrap or pretend the failure was durably recorded. The operational response is fail-closed investigation, not a success repair.

Failure attempts must also meet their original finite <=60-second capture deadline and current identity/fence checks. Rejection or uncertain commit is not a published failure. A worker may obtain a new attempt and reverify; it may not silently restamp the original mismatch. In a concurrent success/failure test where both valid operations complete, final integrity is FAILED regardless of ordering. No health CAS loss can prevent this valid integrity transition. A later authorized credential revision has independent evidence and is never contaminated by N's failure.

Integrity FAILED is sticky across worker restart, epoch change, rename, enable, health success and late preparation. No runtime function deletes/replaces FAILED. Operator repair/reset is outside scope; rotation to a new immutable revision is the bounded recovery path. Retain failure history and linked provenance.

## Privacy, rejection and proof capture

Return only the explicitly allowed capture metadata over the private worker channel and fixed publication results. Do not return row contents, binding differences, existence probes, exception causes or SQL diagnostics on rejection. Worker output/logging must redact capture objects and raw driver exceptions. Use fixed operational categories such as REJECTED/DEPENDENCY_UNAVAILABLE/COMPLETION_UNKNOWN with a random correlation ID; no SQL text, JDBC binds, DETAIL/HINT/CONTEXT, locator, verifier, key versions, role credentials or network response bodies. This defines no HTTP error contract or endpoint. Unexpected transaction/database failures are sanitized at the worker boundary, including commit failures.

Database-server logging needs explicit review too: do not enable parameter/statement/error-context logging that leaks capture arguments or results. SQL permission errors can expose SQL/object names to a direct SQL client; never promise PostgreSQL itself conceals all diagnostics from a trusted LOGIN. “No SQL leaks” acceptance applies to captured worker/application outputs and approved server-log configuration, including failures before/after function entry. Private allowlisted audit storage is not permission to log or serialize it publicly.

Required proof package identifies tested commit/tree, actual baseline migrations and operator installer SQL, PostgreSQL version, catalog ownership/grants/search_path, original-login identity checks, attempt/assertion row allowlists, actual counts/failures/errors/skips, transaction outcomes and redacted captured output. No credential payload, raw SQL exception or successful live-provider claim in the package.

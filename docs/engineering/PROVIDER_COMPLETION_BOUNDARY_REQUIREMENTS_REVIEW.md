## F1 — recorder ordering is an implementation clarification, not a new outcome rule

Register the recorder after establishing a non-null new status, as early as supported synchronization permits, before remaining fallible context checks. The contract requires registration before the body, but does not prohibit this ordering. If owned context validation fails before registration is possible (for example, missing synchronization), attempt rollback only of the owned status. Without the required callback acknowledgement, write classification is UNKNOWN and lookup classification is UNAVAILABLE even if rollback returns normally. With the full rollback acknowledgement conjunction, invalid owned context is UNAVAILABLE. The revised table already establishes this precedence; do not weaken acknowledgement to status flags alone or roll back a null/non-new status.

Acceptance should independently cover owned wrong isolation/read-only/resource with recorder available, missing synchronization or registration failure, rollback throw after context failure, and null/non-new returned status with zero boundary rollback/commit/body calls. Observe delegated manager cleanup where its supported lifecycle permits it. Resource presence never establishes ownership.

## F2 — locate the rollback marker inside the owned transaction

Acceptance mentions body failures rolling back “caller markers.” Ambient caller transactions are refused, so interpret this as a test-only marker inserted inside the owned body transaction before an injected failure, or use actual provider row deltas. Keep the separate ambient marker test: refusal leaves that caller marker and rollback-only flag untouched, and the caller can commit it. No production caller callback is needed. This is fixture wording, not a scope or safety blocker.

## Accepted requirements and implementation gates

- Ownership is determined from the returned new status, never inferred from thread resource presence. Ambient active transaction, synchronization and expected-DataSource binding are refused before manager/body invocation. No REQUIRES_NEW, suspension, caller resource clearing or rollback of unowned status is authorized.
- Freeze phase handling in implementation: proxied body failure is handled before entering the commit phase. Once commit is invoked, any RuntimeException or missing/contradictory confirmation yields UNKNOWN without another rollback. A completion exception carrying ProviderReceiptFailure must not enter the known-body-failure path.
- Confirmed write success requires normal commit return, completed owned status and COMMITTED afterCompletion. Confirmed body rejection requires normal rollback return, completed owned status and ROLLED_BACK afterCompletion. Callback-only or flags-only evidence is insufficient; exceptions override definite callbacks. A normal commit reporting ROLLED_BACK is already UNKNOWN under the table.
- ProviderReceiptFailure's public constructor accepts arbitrary codes/statuses. The exact pair allowlist and enum-derived statuses correctly prevent echoing forged text or mismatched statuses. Existing RECEIPT_UNAVAILABLE500 remains an internal known body failure; this does not establish a public HTTP mapping. Generic write rejection uses COMMAND_UNAVAILABLE503 only after confirmed rollback.
- Explicit lookup invokes findOwn, not probeOwn, exactly once with fresh authorization in owned read-only REPEATABLE_READ. FOUND returns Receipt rather than Result/Probe; ABSENT is released only after confirmed read completion. Only UNAUTHORIZED401, FORBIDDEN403 and INVALID_KEY400 yield lookup REJECTED after confirmed rollback. RECEIPT_UNAVAILABLE/corruption/storage and all other lookup body failures yield LOOKUP_UNAVAILABLE503; read completion uncertainty never releases provisional found/absent data.
- Prepared command/credential provenance remains trusted and unproved by this layer. PREPARATION_REQUIRED needs confirmed rollback before external historical preparation. No key lookup, preparation, retry, compensation, deletion or hidden recovery read belongs here. A preexisting committed receipt survives rejection of another attempt.
- Outcome state/payload constructors, Jackson-ignore annotations and redacted toString need source/QC checks. Retain no input exception, cause, suppressed exception or arbitrary message. Boundary log capture supports only the declared boundary scope; external framework/driver/server logs and fatal Errors are excluded expressly.
- The revised contract correctly confines decorators to the manually constructed boundary dependency; receipt/connection proxies retain the original configured manager. Inject only the owned outer completion. Verify this wiring explicitly so tests exercise completion faults rather than proxy participant faults. “Zero automatic follow-up calls” excludes legitimate earlier proxy participation and prohibits boundary-generated retry/rollback/lookup after the injected completion.
- On both H2 and native PostgreSQL, delegated actual rollback then commit exception and delegated actual commit then exception both yield UNKNOWN. Separate healthy explicit lookup yields ABSENT and FOUND respectively, with exact row deltas and fresh authority. Include acknowledged rejection, rollback acknowledgement failure, afterCommit failure, absent/unknown/contradictory callback, read completion failure for both found and absent, and ambient refusal preserving outer commit. Controlled injection is not live network-partition evidence.

No broader API, policy, health, vault, migration or universal diagnostics acceptance is implied. Contract implementation and runtime verification remain pending; this review reports no test passes.

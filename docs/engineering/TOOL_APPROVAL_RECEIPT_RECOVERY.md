# Read-only recovery of a submitted Tool approval

GET `/api/v1/organizations/{org}/execution-runs/{run}/text-tool-approval/receipts/{key}` resolves only the current ADMIN actor's exact organization/Run/key approval. Current enabled credential-version-matching ADMIN authority is mandatory on every read; another Run/key yields null. No current Start eligibility, open lease, live Tool grant or original credential version is required to read the actor's historical operation. This does not restore execution authority.

The read is repeatable-read and write-free. It validates bounded well-formed UTF-8 historical text, input SHA and the original scope/revision/grant/input fingerprint before returning the immutable Preview. Corrupt data conflicts. Private raw historical input is returned only at this restricted endpoint with no-store, not in generic feeds/logs. Revocation and Run Start do not erase legitimate historical approval evidence.

While an ambiguous command remains in memory, the approval page offers an explicit receipt GET. It compares every verified field with the captured preview before resolving pending. A matching result displays a historical heading and directs the user back to Run details, with no implicit execution grant or Start link. Null does not prove failure and does not discard the exact pending key/body. Denial erases private data. Reload/abandonment still loses in-memory key correlation; listing historical approvals or entering arbitrary keys is outside this slice. There are no automatic writes, retries or provider calls.

Validation includes backend recovery after Start and grant revocation, wrong Run/key, corrupt text and current role denial, inherited by required PostgreSQL wrapper. Mocked browser cases cover GET-only lost-response resolution and null receipt remaining unknown across three widths, plus retained approval/escaping/stale/role cases. Matching-head native and real Vault CI remain separate from local checks. No schema change, merge or deployment.

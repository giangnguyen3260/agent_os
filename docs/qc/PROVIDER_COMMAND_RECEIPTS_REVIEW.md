### Contract interpretation to verify after freeze

The trusted caller's correlation of command metadata with authenticated org/actor/command/secret is a precondition, not something metadata grammar or this DB service proves. Fresh credential metadata has separate org/connection/provider/revision scope. These two preparation products must not be conflated. Historical command-key mismatch requires rollback of the complete joined transaction and release of locks before external re-preparation; PREPARATION_REQUIRED must never trigger an in-method retry. A successful REQUIRED return remains provisional until the actual outer commit.

PR42's current-row mapping includes credential metadata, and its public get path requires a read-only REPEATABLE_READ context. Neither is an acceptable historical replay/projection shortcut inside this READ_COMMITTED write service. Fresh before-state capture must use locked scoped parent/event state, and replay/read must resolve retained events plus the scoped CREATE event without current credential reads. Existing V022 event constraints alone do not enforce the complete event/result matrix: selected-row validation and V023 composite relationships must be inspected separately.

### R1 — Medium: H2 recordedAt is transaction time, not the required post-lock wall clock

`ProviderReceiptService.now()` uses PostgreSQL clock_timestamp() but falls back to `select current_timestamp` for H2. The revised contract explicitly requires a DB wall-clock sample after mutation/locks. H2 in the provided dependency uses one transaction-stable CURRENT_TIMESTAMP; merely executing that expression after mutation does not make its value a fresh wall-clock observation. A joined transaction can have established this value before a long wait, so recordedAt can describe a pre-wait instant. Because PR42 also timestamps with its H2 current_timestamp fallback, ordinary same-transaction mutation tests may still show matching/ordered times and conceal the discrepancy. This finding concerns the required timestamp semantics, not proof of a physical commit time.

QC executed this isolated in-memory dependency probe on OpenJDK 17.0.20 using the provided h2.jar; it did not touch application tables or implementation files:

```sh
java -cp /tmp/agentos-receipt-tools/h2.jar org.h2.tools.Shell -url 'jdbc:h2:mem:qc_clock;MODE=PostgreSQL' -user sa -password '' -sql 'CREATE ALIAS QC_SLEEP FOR "java.lang.Thread.sleep"; SET AUTOCOMMIT FALSE; SELECT CURRENT_TIMESTAMP AS before_wait; CALL QC_SLEEP(150); SELECT CURRENT_TIMESTAMP AS after_wait; ROLLBACK;'
```

Both selects returned exactly `2026-11-01 17:45:44.558497+07`, despite the sleep call reporting 153 ms. Exit status 0. This establishes the actual fallback expression's stable clock behavior; it is not a receipt-service integration test or PostgreSQL timing failure. Required resolution: provide an actual post-lock DB wall-clock implementation for the supported H2 path, or have main explicitly reconcile the contract's H2 versus PostgreSQL semantics. Test a transaction whose clock is established before a controlled wait, then verify the receipt sample against the post-wait bound rather than merely `recordedAt >= after.updatedAt`. No production correction is prescribed by QC without BE/contract-owner selection.

### Ownership and phase gates for source review

The explicit boundary must own completion without a transaction annotation or generic caller callback. Ambient actual transaction, synchronization or expected-DataSource resource binding must refuse both entry points before manager/body invocation. Ownership requires a non-null new status; null/non-new status must never be committed or rolled back by the boundary. No resource clearing, suspension or REQUIRES_NEW is authorized. Tests must preserve an ambient caller's rollback-only flag and allow that caller's own marker to commit.

A newly owned status requires actual transaction/synchronization, expected JDBC resource, actual JDBC isolation and Spring read-only validation before the proxied body. Record completion as early as supported synchronization allows, before remaining fallible checks. Writable READ_COMMITTED and read-only REPEATABLE_READ must be verified independently, rather than inferred from requested definitions. Wrong resource/isolation/read-only with a working recorder, absent synchronization, recorder-registration failure and rollback failure need separate observations. Resource presence is not ownership. Missing callback acknowledgement cannot be converted to confirmed termination just because rollback returned or status reports completed. Supported manager cleanup is the manager's responsibility; a broken begin that leaves unreported resources is outside the declared manager preconditions.

Separate body and completion exception handling. Once commit is invoked, a RuntimeException—including ProviderReceiptFailure—or a missing/contradictory completion confirmation must yield write UNKNOWN. Do not enter a body-failure catch and roll back after that point. A normal operation return, completed owned status and matching local afterCompletion are all necessary; none alone establishes success. A thrown completion operation remains uncertain even after a definite callback. No retry, second rollback after uncertain commit, automatic receipt lookup, second command transaction, key change or external cleanup/compensation is permitted.

### Q1 — Medium: malformed callback can reset the recorder's unobserved sentinel

`Owned.completion` starts at `-1`; `afterCompletion` assigns `completion == -1 ? status : STATUS_UNKNOWN` (observed lines 255–263). A malformed callback carrying `-1` leaves the recorder indistinguishable from never called. A subsequent callback carrying COMMITTED sets completion to COMMITTED, so normal manager return plus completed status can incorrectly release COMMITTED/FOUND/ABSENT despite malformed duplicate reporting. Likewise `-1` followed by ROLLED_BACK can incorrectly confirm a rejection or invalid-context cleanup. This is a direct source-derived counterexample, not an executed runtime failure or evidence that a normal Spring manager emits such callbacks.

The contract explicitly includes malformed/unknown completion reporting in acceptance. Require observation state independent of the received integer and permanently invalidate duplicate/unsupported reports; a malformed first observation must not permit a later valid callback to restore confirmation. Add focused assertions for malformed `-1` followed by matching committed/rolled-back reporting, alongside ordinary UNKNOWN, absent and contradictory reporting. Keep the recorder nonthrowing. Write uncertain completion must remain UNKNOWN, read uncertain completion UNAVAILABLE, with no provisional result and no fallback manager/body/lookup calls. **Provisional source acceptance is held for this concrete recorder defect and later frozen-source/test retest.** QC makes no implementation edit.

### Requested ownership/phase paths inspected

- Pre-body context failure: after non-null/new status, the recorder is registered before remaining resource/isolation/read-only checks when synchronization is available. Checked/runtime exceptions within that validation retain the owned status with valid=false. Write then attempts exactly one owned rollback and requires normal return, completed status and ROLLED_BACK callback for UNAVAILABLE; otherwise UNKNOWN. Read attempts the owned rollback and returns UNAVAILABLE. Missing synchronization leaves the recorder unacknowledged and therefore cannot manufacture a confirmed write rollback. This agrees with requirements F1, subject to Q1 and actual fault tests.
- Null/non-new returned status: begin returns null immediately, before recorder/body/commit/rollback. No caller resource cleanup or rollback-only mutation is present. The boundary relies on the declared manager lifecycle preconditions rather than attempting to repair a broken manager or status implementation. Ambient actual transaction, synchronization and expected resource binding are checked before manager invocation.
- Commit-phase ProviderReceiptFailure: the receipt-body try/catch ends before commit. commit catches ordinary RuntimeException and returns false; executePrepared maps this to UNKNOWN without rollback, allowlist evaluation or retry. lookupOwn maps the same failure to UNAVAILABLE. Therefore a commit-thrown UNAUTHORIZED failure cannot enter the known-body rejection path in this source.
- Completion confirmation: commit/rollback check both completed status and the matching recorder value after normal manager return. Exceptions override callback/status evidence. Duplicate ordinary valid statuses poison the recorder as UNKNOWN; Q1 identifies the malformed sentinel exception to that intended behavior. No hidden second transaction, automatic receipt lookup or compensation path appears.

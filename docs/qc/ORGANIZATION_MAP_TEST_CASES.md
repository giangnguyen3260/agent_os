## Fixture recipe and execution rules

Create organizations A/B; enabled current ADMIN A, MEMBER A, nonmember B; independently vary disabled flag, credential version, deleted membership and unsupported role. Use canonical lower-case v4 IDs (also test accepted v1–5). A has 41 Teams: include duplicate and case-fold-equal names with deterministic UUID tie breakers, DRAFT/ACTIVE/ARCHIVED, null purpose/intake/manager, unknown stored status. One Team has 41 Agents, another has zero, and A has 21 unassigned Agents. B has distinguishable secret names/IDs. Include literal `%`, `_`, `!`, backslash and mixed-case search values. Record expected IDs/counts from fixture manifest rather than computing expected values with production query logic.

Use existing seed/test harness conventions; fixture creation is setup, not a map write. Normally valid reporting cases: same-Team target, cross-Team target, foreign-org target, self-link, two-node cycle, same-org both unassigned and unassigned→assigned. Invalid manager/foreign attachment fixture requires explicitly isolated corruption path due V005; mark BLOCKED if unavailable. Never relax production constraints. Count manager as an assigned Agent once. Keep fixture immutable across static pagination cases; concurrent insertion/deletion belongs only to snapshot cases.

For API cases send GET `/api/v1/organizations/{A}/organization-map` (O) and `/api/v1/organizations/{A}/organization-map/agents` (G), authenticated cookie for named actor; assert HTTP status, JSON data exact keys/types/identity, and absence of B secret strings/IDs anywhere in payload/error. Use a raw HTTP client for duplicate parameters; a JS object cannot represent duplicates. Preserve raw request URL with evidence.

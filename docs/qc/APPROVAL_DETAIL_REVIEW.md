## Concrete findings for coordinator

### F1 — High: reused detail route loses frozen request and can retain prior detail under new IDs

`approval-detail.component.ts:83-87` assigns new organization/approval IDs and unconditionally discards `frozen` before `load()`. `load():104` returns immediately when busy, before clearing state or incrementing epoch. A same-route parameter navigation during submission can therefore leave the prior request's private detail displayed under new IDs, discard the only retry key, and leave the prior mutation callback active. POST completion validation at 260 reads mutable `this.approvalId`; a valid response for the original request can become an unverifiable response without a frozen retry. An uncertain parameter change also discards the key while retaining `uncertain`, yielding a retry button whose handler has no request.

`app.routes.ts` registers canDeactivate, but the default Angular reuse of the same route configuration on parameter changes does not deactivate the component. `runGuardsAndResolvers: 'always'` does not by itself turn reused routes into deactivations. Thus the existing canLeave method does not cover this path. This is a source-derived lifecycle finding, not a browser reproduction or demonstrated backend authorization bypass.

**Fix:** protect same-component parameter transitions before overwriting IDs/discarding submission state; cancel/reject navigation while ambiguity remains unless the user explicitly confirms abandonment. Capture org ID, approval ID, actor and exact operation/body/key together as immutable submission identity; use captured IDs for POST, response verification and retry. Immediately invalidate old callbacks and clear private detail on an accepted scope change, even when busy. Ensure new context resets busy/uncertain/outcome coherently. Add AD37/AD38 coverage using Router parameter navigation while POST is pending and while uncertain, including cross-org reuse.

### F2 — High: definitive retry errors incorrectly erase an earlier ambiguous outcome

`approval-detail.component.ts:280-296` clears frozen/uncertain for every 400/401/403/404/409. Sequence: original POST commits but its response is lost; grant is revoked; identical retry receives the contractually correct fresh-authorization 403. The UI now forgets the original key and unknown result. A 409 after an unknown result likewise cannot establish that the first POST did not commit. The error branch can even say “Decision was not accepted,” which is not justified for the original attempt.

**Fix:** distinguish first-attempt definitive refusal from an already ambiguous submission. After ambiguity, retain the immutable submission and unknown-outcome warning on retry denial/conflict; stop unauthorized retry controls as appropriate, but do not claim nonacceptance or allow a replacement operation based on that refusal. Reconcile only with a verified authoritative decision or explicit user-confirmed abandonment. Pair real backend fresh-revocation replay with UI response-loss coverage (AD23/AD36).

### F3 — Medium: failed reconciliation still exposes a mutation retry after access denial

`load()` preserves frozen/uncertain; `failure():172-183` clears result/context and sets denied for 401/403/404. The unconditional uncertain section at HTML 83-105 still offers “Retry same decision,” disabled only for busy/loading. `retry():230-231` does not require current context, permission or non-denied state. After a reconciliation GET establishes lost access, the page therefore continues offering and sending a decision POST with retained private reason/body. Server checks must deny it, so this is not an authority bypass; it is an actual FE privacy/control defect and an avoidable mutation attempt after known access denial.

**Fix:** preserve the minimal unresolved-outcome warning from F2 while suppressing mutation retry after fresh access denial. Clear editable reason/stage/acknowledgement on denial and define how pending private submission material is retained or discarded on lost access without silently asserting success/failure. Account change already clears frozen state; maintain that isolation. Cover GET403 during uncertain reconciliation and prove no POST follows its retry UI.

### F4 — Medium: valid nullable approved reason is rejected by FE

`approval-detail.service.ts:24-33,64-84` requires Decision.reason to be a string. The contract permits nullable reason and current backend `ApprovalDetailService` strips a supplied reason but preserves null, inserts it and projects it through Decision. An API-approved decision submitted with reason=null is valid yet detail validation rejects it. FE's own submissions use empty string, so the immediate native approve happy path avoids this, but another valid client can make the recorded detail unreadable. Reconciliation comparisons also require exact reason equality without a declared null/empty normalization rule.

**Fix:** align nullable Decision/DecisionBody types and validators with the final fixed DTO; allow null only where appropriate (never blank/null rejection reason), and use the agreed canonical reason representation consistently for response verification and reconciliation. Recheck once DTO finalizes; do not silently narrow the contract to FE's empty-string producer.

### F5 — Medium: full-page exit/reload has no ambiguous-outcome warning

Only router `canLeave()` is registered (`component.ts:307-317`, routes). No beforeunload handling exists in the reviewed detail implementation. Browser reload/tab close loses in-memory body/key during pending or unknown POST without the required warning. SPA deactivation protection does not cover full-document navigation.

**Fix:** register/clean up a beforeunload guard when busy/frozen (and optionally dirty); use browser-native warning semantics. Do not persist authority/reason to localStorage. Browser coverage should distinguish router navigation, reused parameters and document unload. Browsers constrain unload prompts, so report observed behavior rather than promising guaranteed interception.

## Policy status and bounded scope

The authorized next flow permits engineering and QC to proceed. Invitations were previously open; Figma examples are not policy approval. Record the following as proposed engineering defaults: current same-org HUMAN ADMIN issues MEMBER-only invitations; fixed 72-hour invitation lifetime; 60-second resend cooldown; email bearer token; SMTP replacement behavior; new-account password/name collection. Do not label them approved business policy. Their exact failure behavior must nevertheless be specified before implementation.

Preserve these boundaries: no Owner/new Admin, Team/Agent membership or approval grant; no automatic login; no existing-account profile/password/enabled/version/session changes; no organization creation or general signup. Existing explicit grants and other-organization memberships remain unchanged. Rejoining can make previously retained grants eligible again under existing grant checks: disclose this consequence, without revoking/reactivating/reissuing grants or claiming that MEMBER means no approval authority.

## Required corrections before implementation

| ID / priority | Concrete risk | Required contract correction |
| --- | --- | --- |
| R1 / blocker | Anonymous acceptance can overwrite an account created after inspection or by another organization invitation. A missing account row cannot be row-locked. | Use the same trim/lowercase Locale.ROOT identity normalization as login/recovery; no provider alias folding. Serialize absent-email creation across organizations using a documented transactional email-key lock or equivalent uniqueness-and-full-transaction-retry protocol. Unique `human_accounts.email` is the final invariant. Re-resolve after waits. If an account now exists, anonymous acceptance must stop and require exact-account login, preserving the invitation; never upsert credentials/profile or silently attach an unauthenticated existing account. |
| R2 / blocker | Removal/rejoin can resurrect an old role-change command with the same MEMBER role and revision. | In the acceptance transaction, retain and lock `member_role_ledgers(org,account)` and advance revision on every actual membership insertion, including first join (absent ledger 0 → 1) and rejoin (r → r+1). At maximum revision fail atomically; never wrap/reset/delete. A repeated accepted request or already-present member must not advance again. Future removals must also advance this protocol before delivery. |
| R3 / blocker | Copying the recovery worker's account→job order and later taking an organization lock creates a human→org inversion against role management. FK checks and worker claim updates can acquire locks implicitly. | Every invitation writer/dispatcher needing org and humans uses READ_COMMITTED: organization mutex first; discover identities without mutation; distinct existing human UUID string locks in global sorted order; scoped membership locks in matching order; retained role ledger and invitation/job/token locks in one documented order. No actor-first lock. All paths, including resend/revoke/retry/audit and cross-org same-email creation, must fit one complete lock graph. A new email-key lock must have a fixed place in that graph and cannot be acquired after one path already holds a human while another holds it before that human. Recovery/login need not take org locks; never make them do so indirectly. |
| R4 / blocker | Issuer demotion/disable/reset during lock waits permits stale authority to enroll members. A replacement sender must not accidentally transfer authority. | Bind immutable issuing org, issuer account and normalized recipient identity to the invitation. After all waits, require original issuer currently enabled and ADMIN in this org. For authenticated acceptance also recheck recipient enabled, exact account/email and current session credential version under its human lock. For admin mutations recheck acting enabled/version-matching ADMIN. Specify whether issuer credential changes invalidate invitations; recommended bounded default is current issuer enabled/Admin, without treating issuance credential version as permanent authority. Another Admin's resend does not silently replace original issuer. |
| R5 / blocker | Revoke, accept and replacement delivery can each succeed against stale status; inspect is mistaken for a reservation. | Serialize on the same org/invitation lifecycle. Recheck token generation, unconsumed status, revocation, absolute expiry, issuer and target state after waits. Membership insertion, revision advancement, acceptance marker, cancellation of pending mail, token invalidation and safe audit commit atomically. Audit failure rolls back all. Revoke committed first prevents acceptance; acceptance committed first is historical success and revoke cannot remove membership. Define the latter response explicitly. Inspect never reserves acceptance. |
| R6 / high | “Fixed 72h” can accidentally become dispatch-time or resend-time expiry, and delayed SMTP can activate an expired/revoked token. | Store one immutable `expiresAt` from committed issuance; every generation shares it. Use one post-wait microsecond UTC decision time, valid only while now < expiresAt. Resend/retry never renews it. Dispatcher rechecks expiry/revocation/acceptance and issuer before send; no late callback can re-enable terminal state. A fresh invitation after expiry/revoke is a separate issuance with new identity and explicit policy. |
| R7 / high | Durable mail with no raw token cannot resend the identical token after restart; SMTP ACK is not atomic with DB commit. | Persist job metadata/digest generations only. Generate 32 random bytes in worker memory per attempt; store only SHA-256 token digest. Preserve the last committed delivered generation until replacement SMTP ACK **and transaction commit**. Failure deletes only the attempt generation. Crash after ACK before commit may deliver an unusable link; retries generate another token. State SENT means SMTP accepted, not inbox delivery or exactly-once mail. Never promise old links become invalid at the external ACK instant. |
| R8 / high | Public endpoints are currently denied by default; a broad auth matcher or org exception exposes unrelated surfaces. | Add only exact inspect/accept transport paths to permitAll; retain CSRF for both POSTs and all admin writes. Keep admin APIs under existing org guards plus service-level fresh ADMIN checks (GET org guard alone permits MEMBER). Do not put anonymous redemption under membership-required org transport. No token in path/query/GET validation, redirects, logging or exception echoes. Reuse trusted configured HTTPS frontend URL validation rather than Host-derived links. |
| R9 / high | Already-member/disabled/mismatched-login handling silently downgrades an Admin, re-enables an account, or discloses global profiles. | Existing same-org membership is never updated by invitations, especially existing ADMIN. Recommended: do not issue to a current member; if membership appears before accept, return a bounded already-member/conflict outcome with no role/revision/credential mutation. Existing disabled accounts cannot accept or be re-enabled. Wrong logged-in account cannot create or join another account; require explicit logout/login, never switch automatically. Admin issuance/list outcomes must not disclose global existence, enabled state or foreign memberships. |
| R10 / high | Lost replies and token replay create duplicate joins or expose accepted-account details. | Choose explicit acceptance retry semantics: either invalid/consumed response with honest unknown-success UI, or an authenticated, narrowly scoped historical receipt. Do not return a global profile or reusable session to anyone holding a consumed token. Unique membership and lifecycle constraints must guarantee one join/revision increment. Admin create/resend/revoke also need exact duplicate/unknown-outcome behavior; never automatic browser retries that create another invitation. |

R2 does not permit inventing a V014 role-change event for ABSENT→MEMBER: its constraints require two different ADMIN/MEMBER roles. Retain existing role events/receipts untouched; record invitation membership provenance separately and allow honest revision gaps in role-only history. A historical old role receipt can still describe an earlier success; it must never reapply a role change to a rejoined membership.

## Exact API details the coordinator must close

- Define one active invitation per `(organization, normalizedEmail)` or explicitly specify multiple-invitation behavior. Recommended bounded default: one active lifecycle; concurrent create/resend cannot bypass cooldown or produce multiple independently redeemable invitations. Cooldown is durably serialized, checked after waits and scoped independently from password-recovery buckets. State whether throttled attempts change the next eligible time.
- Enumerate lifecycle states separately from delivery state. Pending delivery is not delivered; delivery failure is not revocation; accepted/revoked/expired never become pending again through resend. No SMTP should occur in public inspect/accept or admin request handlers.
- Fix strict UUID/JSON/enum/unknown-field/null/duplicate-field rules, size limits, status/error precedence and safe response DTOs. Preserve security-filter 401/CSRF 403 precedence rather than promising universal controller ordering. Unknown/malformed/expired/revoked/consumed public tokens should have a common safe invalid-link response. Token holders may see only the minimum org/recipient context required to accept, never issuer private profile or global-account lookup details.
- A public inspect response may indicate required login versus new-account entry to its bearer if explicitly chosen; document this limited token-holder disclosure. It must not become an unauthenticated email-existence API. Inspection may become stale immediately. Accept must re-evaluate everything.
- New-account fields are accepted only on the still-absent-account path. Validate display name with explicit trim/codepoint/control/surrogate rules and fit the existing 255-character column. Password minimum is 14 Unicode code points, maximum 72 UTF-8 bytes, BCrypt cost 12; reject malformed surrogate input rather than encoder replacement. Define whether extra new-account fields on existing-account acceptance are rejected; recommendation: reject them, never ignore credential overwrite attempts silently.
- Authenticated existing acceptance adds membership only. Anonymous new acceptance creates account and MEMBER membership atomically and leaves the browser anonymous. Login remains explicit. Neither path clears recovery tokens/throttles, increments existing credential versions, revokes sessions or modifies grant ledgers. New account IDs must be fixed before lock planning if needed; FK lock acquisition must not introduce an unplanned human lock.
- Sender/recipient display strings must be escaped; no arbitrary HTML or mail-header input. Fragment is erased immediately and token remains memory-only; no storage, telemetry, referrer/query forwarding or automatic accept on load. Inspect does not consume token, so mail scanners cannot join. Refresh after erasure explains that reopening the email is necessary. After explicit login refresh CSRF; preserve token only in live flow memory or ask to reopen the email, never place it in a login return URL.
- Admin UI follows existing focus/visibility/account/route freshness and late-response privacy rules. Clear invitation email/token/password on identity change and terminal navigation. Distinguish queued mail, SMTP acceptance, membership committed and refreshed current membership. Do not claim instant cross-tab revocation.
- Set bounded attempts, mail timeout, public-token/IP/global abuse controls and retention responsibilities. High-entropy tokens do not prevent mail bombing via an Admin account or broad endpoint abuse. Keep recipient email restricted to invitation administration/mail delivery; generic audit contains identifiers, never email/token/password/body. Use additive migrations; do not edit V001–V014.

## Required QC evidence (prospective, not executed)

1. Real PostgreSQL overlapping anonymous accepts for the same normalized email across two organizations: exactly one account; loser requires login; no overwritten hash/name/enabled/version, no partial join or consumed invitation. Include unique-conflict recovery with a fresh transaction, not continued work in an aborted PostgreSQL transaction.
2. Same-token double accept; accept/revoke in both serialization orders; accept/replacement dispatch; issuer demotion/disable concurrent with accept; recipient reset/disable concurrent with authenticated accept. Barrier tests must demonstrate post-wait checks, rollback and bounded completion.
3. Cross-org reciprocal issuer/recipient UUID ordering, invitation worker versus role management and recovery/login, email-lock versus human-lock races. H2 or a happy-path request is insufficient lock evidence.
4. Retained revision r followed by actual rejoin gives r+1; an old uncommitted role command at r conflicts even if current role is MEMBER. Existing accepted role receipt remains historical. Maximum revision and audit failure leave no account/membership/token/job partial writes; already-member cannot demote ADMIN.
5. Mail outage/retry and worker restart: prior committed delivered token remains usable until committed replacement; fixed original deadline persists; revoke/accept cancels jobs; crash/ambiguous ACK limitation is reported honestly. No raw token or body in durable job, DB, logs or browser storage.
6. CSRF/method/route negatives, anonymous admin access, MEMBER admin GET denial, foreign-org isolation, mismatched and stale session identity, disabled recipient, uniform invalid-link DTOs, strict wire validation, Unicode/UTF-8 limits and trusted-URL rejection.
7. Real-browser 1440/768/390 flow for existing and new accounts, explicit login/no auto-login, fragment erasure/reload/reopen, queued-versus-delivered states, failed/malformed/lost responses, wrong account and late callbacks. Preserve previous auth/grant/role regression suites; identify exact candidate and distinguish planned checks from executed results.

## Assessment

The proposed MEMBER-only invitation scope is compatible with the existing authority model if the corrections above become enforceable contract clauses. Blockers are atomic absent-account creation, retained revision advancement, one complete lock graph, fresh original-issuer authority and lifecycle serialization. No hypothetical policy confirmation is needed to continue bounded engineering; unresolved business defaults must remain labeled as such. This report is not approval of an API draft that was not yet available or evidence that its implementation passes these gates.

### Remaining bounded contract corrections

1. **Invitation revision overflow on acceptance (hard precision gap).** Resend/revoke reject revision overflow and expectedRevision is bounded at2147483647, but acceptance unconditionally says “increment invitationrevision” without explicitly applying that bound. Add: acceptance at maximum management revision returns409 and atomically preserves account/membership/ledger/token/jobs/events. Apply a schema upper bound as well as the post-wait service check. Do not rely on a database integer-overflow500, and do not consume an existing-member invitation past the bound. This is independent of the already-correct member-role-ledger overflow rule.
2. **Disabled-recipient public inspection (contradictory wording).** The final UI paragraph includes “Anonymous inspect may give401 only for existing-disabled?” before saying generic400; the normative inspect paragraph also describes SIGN_IN for an existing anonymous account without its disabled exception. Remove the question and state one rule: a disabled recipient yields generic400 INVALID_INVITATION during inspect and accept, irrespective of caller, subject to ordinary transport/CSRF precedence; no NEW_ACCOUNT/SIGN_IN state or401 for that case. This follows the active contract's stated choice, rather than adding a new policy.
3. **Retained-grant warning (pending coordinator edit).** The reviewed text states grants remain unchanged but does not yet include the promised generic warning in both admin and public review. Add wording that an existing account rejoining may regain eligibility through previously retained explicit grants, subject to all current grant/scope/self/snapshot checks. Do not disclose grant inventory publicly or imply the invitation creates a grant. This is a user-facing implication of the existing model, not a request to change grant behavior.

### Implementation/QC clarifications, not new policy blockers

- Recheck latest issuer/version **after** the org lock and derive the sorted lock set from that serialized invitation state. Do not discover issuer before waiting for the org and then lock a stale issuer after another Admin's resend. Service freshness must cover public inspect as well as accept; the authentication filter alone is not the transactional authority check.
- Management idempotency fingerprints need fixed canonical field lists/vectors. In CREATE, a server-generated invitation ID must not enter the request fingerprint in a way that changes on retry; resolve the historical receipt before generating a new identity. Bind operation and scoped target for resend/revoke exactly as specified. This clarifies the existing exact-replay requirement.
- Demonstrate the intended reauthorization behavior directly: demotion/reset of A blocks old capability; B's committed resend restores eligibility to that same still-delivered capability even if replacement SMTP fails; subsequent B credential-version change blocks it again. Replayed historical resend must not rebind issuer or queue another job. UI review should explain that resend reauthorizes outstanding links; do not describe it as immediate token rotation.
- Test existing ADMIN/MEMBER acceptance as a no-op on membership and role ledger while still consuming/incrementing the invitation lifecycle; preserve existing credentials, sessions, grants and previous role receipts. Test lost reply on this path too.
- “No approval grant created” and “no runtime effect” describe the bounded write scope; they must not imply that restored membership cannot affect eligibility under existing retained grants. The generic warning above addresses this distinction.

Assessment: R1–R10 are addressed by the active design, including the explicitly chosen alternatives for R4/R9. The three bounded corrections above remain visible from the reviewed text. No new business-policy approval or original-issuer restriction is requested. Lock/race/delivery behavior remains prospective until demonstrated on the actual candidate.

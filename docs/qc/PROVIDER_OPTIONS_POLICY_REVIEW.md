### CLI3 — high: missing-row first lock permits second-statement snapshot to use an unlocked new singleton

The replacement transaction executes `SELECT id ... WHERE id=1 FOR UPDATE`, then unconditionally executes the clock/decision/update CTE in a new RC statement. The first statement's result is neither retained nor checked. If singleton is absent in that statement, no row lock was acquired. A concurrent provision can commit before the second statement, which can then see and replace that new policy rather than return missing/unavailable. This violates the promised lock-before-clock/decision sequence on that path.

More serious source-derived interleaving: first lock sees absence; another transaction provisions revision1; a different writer locks it and starts changing revision1 to2; the CLI's second statement can read the last committed revision1, classify expected1 as UPDATE, then wait at its UPDATE. The UPDATE predicate checks only id1 and precomputed outcome; it does not repeat expected revision against the finally locked row. The design can therefore apply a stale decision after waiting, increment a newer row and overwrite the other writer's selection. The clock also precedes that actual update-lock wait. Exact PostgreSQL execution/interleaving remains to be reproduced natively; do not label this a passed or failed runtime race test yet.

Required correction: bind the decision to a successfully locked singleton and return fixed UNAVAILABLE immediately when the first lock found none, before any second-statement read can adopt a newly inserted row. Preserve a later clock statement only after proven lock acquisition; do not add a hidden retry or independent transaction. Add native controlled absent-lock/concurrent-provision and subsequent competing-CAS tests, assert full policy row and exact revision/result. Existing-row CAS/no-op tests alone miss this entry path.

### Test design cautions and pending evidence

Native PostgreSQL is required for singleton arbitration, quota locking/final-slot contention, post-lock clock freshness, observed-wait authorization loss and RR behavior. H2 transaction-stable current_timestamp is structural coverage only. Avoid wall-clock sleeps as the sole proof of ordering: use latches/barriers plus independently observed lock waiting and bounded timeouts. Compute expected quota values independently of implementation helpers, and compare every stored value, not just counts or presence of a secret sentinel. A quota row's FK insertion may acquire referential-integrity locks; inspect the full lock order and bound contention tests rather than assuming application SELECT text is the entire lock graph.

For CLI review, validate argument rejection before subprocess launch, canonical expected revision and SQL literal construction; ensure the CAS clock is a second statement after the lock, psql errors cannot publish success, output parsing/completion uncertainty is fixed and never retried, and --sql-only is read-only SQL emission. No trusted writer action should be run against user/production storage by QC.

### CLI1 — high: show bypasses selected-policy validation and reports corrupt state as confirmed

`sql_for(show)` directly projects `policy_json()` for any id1 row. Unlike replacement, it does not validate positive revision, non-null/exact flags, at-least-one-enabled, timestamp order or finite timestamps. The updated contract expressly requires selected infinite/malformed timestamps to fail closed in operator SQL. PostgreSQL timestamp infinity is allowed by the migration's ordering constraint, so this gap does not require disabling every schema constraint: an otherwise well-shaped row with created_at=updated_at=infinity can still be shown as CONFIRMED. The Python layer also accepts revision0/all-disabled output as successful.

Reproduction at the Python subprocess boundary: zero exit and stdout `{"status":"CONFIRMED","revision":"0","providers":{"OPENAI":false,"ANTHROPIC":false,"GOOGLE_GEMINI":false}}` yields exit0 and reprints that object. This independently proves output-validation weakness; the infinite-row path is a source-level SQL finding, not an executed PostgreSQL result.

Required correction: apply the same selected-row validity predicate to show as to replacement, including finite ordered timestamps, and report fixed UNAVAILABLE without invalid policy fields. Preserve UNPROVISIONED only for genuine absence. Native test infinity, broken selected fields and healthy show; verify no stored value changes. CLI output validation alone cannot validate timestamps because they are not in its public output.

### CLI2 — high: parser accepts incomplete/unexpected payloads and does not contain all malformed-type failures

`main` filters stdout down to lines beginning with `{`, parses one line and checks only membership of `response.get('status')` in a set. It then reprints the entire parsed object. Independently reproduced:

| Mocked successful psql stdout | Actual CLI result |
| --- | --- |
| `{"status":"CONFIRMED"}` | exit0, incomplete object printed as confirmed |
| `{"status":"CONFIRMED","diagnostic":"unexpected internal output"}` | exit0, unexpected field forwarded |
| `unexpected output` followed by `{"status":"CONFIRMED"}` | extra non-JSON stdout ignored, exit0 |
| `{"status":[]}` or `{"status":{}}` | uncaught TypeError, no fixed UNCONFIRMED result |
| duplicate status keys with otherwise valid CONFIRMED object | silently accepted by default JSON parser |

The TypeError occurs because membership hashes the attacker/malformed value before type validation; it is outside the caught OSError/ValueError/TimeoutExpired set. A real invocation would propagate a traceback. Unknown field forwarding also violates the intended fixed, non-diagnostic output boundary if unexpected process output ever reaches it; this is not evidence of actual database credential leakage.

Required correction: validate exact operation/status-specific object shapes, status string, canonical positive bounded revision, exact three boolean provider keys and a nonempty enabled set; reject duplicate keys, unexpected fields and unexpected stdout. Emit a newly constructed allowlisted output rather than arbitrary parsed input. Allow explicitly expected lock-command output through a defined protocol, preferably suppress it in SQL. Treat all malformed payload types as fixed UNCONFIRMED/exit2 without broad swallowing of unrelated programmer failures. Validate expected operation consistency (for example provision's confirmed revision1/selected set). Add mocked process/timeout/nonzero/parse/type tests alongside native successful output tests. Do not automatically retry.

### CLI3 — high: missing-row first lock permits second-statement snapshot to use an unlocked new singleton

The replacement transaction executes `SELECT id ... WHERE id=1 FOR UPDATE`, then unconditionally executes the clock/decision/update CTE in a new RC statement. The first statement's result is neither retained nor checked. If singleton is absent in that statement, no row lock was acquired. A concurrent provision can commit before the second statement, which can then see and replace that new policy rather than return missing/unavailable. This violates the promised lock-before-clock/decision sequence on that path.

More serious source-derived interleaving: first lock sees absence; another transaction provisions revision1; a different writer locks it and starts changing revision1 to2; the CLI's second statement can read the last committed revision1, classify expected1 as UPDATE, then wait at its UPDATE. The UPDATE predicate checks only id1 and precomputed outcome; it does not repeat expected revision against the finally locked row. The design can therefore apply a stale decision after waiting, increment a newer row and overwrite the other writer's selection. The clock also precedes that actual update-lock wait. Exact PostgreSQL execution/interleaving remains to be reproduced natively; do not label this a passed or failed runtime race test yet.

Required correction: bind the decision to a successfully locked singleton and return fixed UNAVAILABLE immediately when the first lock found none, before any second-statement read can adopt a newly inserted row. Preserve a later clock statement only after proven lock acquisition; do not add a hidden retry or independent transaction. Add native controlled absent-lock/concurrent-provision and subsequent competing-CAS tests, assert full policy row and exact revision/result. Existing-row CAS/no-op tests alone miss this entry path.

## Findings and concrete fixes

### F1 — Medium: one purported FK test can pass solely on a CHECK violation; tuple rejection coverage is incomplete

Evidence: `ProviderConnectionFixture.databaseRejectsCurrentCredentialForeignTuple` (lines 670–685) changes the first connection's credential revision from 1 to 2 while leaving configuration revision 1. V022 line 27 independently rejects `credential_revision > configuration_revision`; asserting only `DataIntegrityViolationException` does not establish that the current FK rejected the pointer. This case could pass even if the current FK were absent. The disabled-pointer test uses configuration revision 2 and is stronger for missing revision and wrong provider, but neither case isolates organization mismatch. Another connection having revision 2 does not itself prove all tuple components.

Fix: keep all CHECKs satisfied (advance configuration revision too), arrange an otherwise valid version under the wrong organization/connection/provider, and assert the named `provider_connections_current_credential_fk` or PostgreSQL SQLSTATE 23503 plus constraint identity. Cover enabled and disabled missing/current foreign tuples, with exact before/after rows. Run against native PostgreSQL. The production FK itself is correctly composite and immediate; this finding concerns evidence, not a demonstrated DDL escape.

### F2 — Medium: native authority tests prove fixture serialization, not the actual authority-writer compatibility gate

Evidence: `ProviderConnectionPostgresIT.authorityIsRecheckedAfterObservedOrganizationLockWait` holds an organization lock, observes a pending writer through `pg_blocking_pids`, invokes fixture `revoke` SQL, then commits. This is meaningful independent-transaction coverage for all four authority losses. It does not invoke role-management or recovery services, or observe waiting directly on the account/membership lock. The snapshot test concurrently creates a connection but does not revoke authority within the established read snapshot.

Fix: add coordinated native cases invoking the actual role-change and credential-reset writers, including account-lock waiting with the organization already held by persistence; verify serialized permitted-before-revocation versus forbidden-after-revocation outcomes and exact persistence rows. For disable/removal, explicitly record that no production writer was located, and retain the direct-SQL tests as simulations rather than actual writer coverage. Add read-snapshot revocation evidence: the established snapshot may retain authority, while a subsequent operation must deny it. Keep bounded timeouts and observed blockers; do not replace these with sleeps or mocks.

Source compatibility result: `MemberRoleManagementService.mutate` lines 259–325 locks organization, sorted distinct accounts, then memberships before role update. Same-organization operations serialize at the organization row, so the provider's single-account order is compatible. `RecoveryService.confirm` lines 114–165 locks account before token/update/session work and does not subsequently request organization/membership/provider locks. Provider holds organization then waits on that account without a reverse dependency in this reviewed path. `HumanAuthenticationProvider.verify` locks account then authentication-attempt state, with no later organization lock in the inspected flow. `InvitationStore.orgLock/humanLocks` uses organization → sorted accounts → memberships. Repository source searches found no production account-disable or membership-delete implementation; compatibility for absent/future writers cannot be certified. This is a bounded path assessment, not a proof about arbitrary caller-held locks or every application transaction.

### F3 — Medium: all-row/all-operation acceptance assertions remain weaker than the normative evidence requirement

Evidence: `createReloadAndAllowlistedStorageForEveryProvider` checks exact column names, metadata fields, selected connection values, counts and unchanged existing tables. `mutationsRetainVersionsAndPreserveImmutableOptions` checks retained version equality, selected immutable properties, event kinds and revision sequences. Neither compares every new-table cell with a complete expected row set for every successful mutation. In particular, event actor/time/provider/mode/name/workspace/state and all parent/version timestamps are not comprehensively checked. Existing-table snapshots are compared for create only, not the mutation/rejection/rollback matrix. Sentinel/base64/hex absence supplements these assertions but cannot prove arbitrary secret absence.

Fix: construct complete expected parent/version/event maps (capture generated IDs and declared timestamps), compare all columns and retained rows after each mutation, rejection, event failure, losing CAS and joined rollback; compare controlled existing-table snapshots across those paths too. Include all providers and Anthropic null/non-null workspace. The native CAS test currently establishes one success/one conflict, revision 2, two events and one version; strengthen it to match the winner's exact parent/event snapshot and unchanged retained version. No production rewrite is indicated by this gap.

### F4 — Medium: safe method exceptions do not cover transaction-completion diagnostics

Evidence: `ProviderConnectionService.safe` sanitizes statement/mapping failures to cause-free fixed `ProviderConnectionFailure` codes, but executes inside Spring's transactional method interceptor. Owned transaction commit occurs after `safe` returns; joining commit occurs later in the caller. Commit/connection failures can therefore emerge as framework exceptions outside this wrapper. There is no test of commit-time exception shape or captured JDBC/framework logs. The contract's broad safe-diagnostics requirement is not established for this boundary by inspecting `safe` alone.

Fix: define and test a transaction-completion error boundary for owned and caller-owned transactions, preserving uncertain-outcome semantics without retry or compensation. Ensure the consuming boundary emits only fixed safe diagnostics and does not log nested JDBC exceptions/bind values; verify with captured logs and injected completion failure. A service-body catch cannot sanitize a later outer commit. This review demonstrates a coverage/ownership gap, not an observed secret leak: the stored values are prepared metadata and no raw key enters this service. Do not turn an uncertain commit into a definite local rejection claim.

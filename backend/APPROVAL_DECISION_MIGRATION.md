# V011 sealed preview decisions

V011 is additive after the V010 metadata ledger. Existing requests acquire a nullable human requester field and remain readable. No production requests, snapshots, action heads or grants are seeded. Metadata-only rows and legacy APPROVED rows never become decision or execution authority merely because of this migration.

New tables hold current action heads, sealed snapshots, explicit expiring/revocable scoped grants, immutable-by-API decisions and actor/organization-scoped idempotency receipts. The decision transaction updates only its approval status/timestamp and appends one decision, safe audit event and receipt. Task/Mission state, provider calls and worker execution are unchanged. There is no public snapshot producer or grant writer. Manage future trusted producer and grant-management capabilities under a separate authorization/audit contract; do not use disposable CI fixture SQL as a production bootstrap.

The initial supported action schema is PUBLISH_PREVIEW. Its complete bounded parameters are destination=internal-review, visibility=TEAM and a restricted resourcePath. These parameters must be shown to the human alongside descriptive target/scope/effect text. New action types, arbitrary provider parameters and credential-bearing payloads fail closed until separately reviewed. Canonical serialization binds request/action identities, org/Team/Mission/Task, human/Agent requester, type/risk, head revision, snapshot version/expiry, all complete parameters and optional cost. Java recomputes SHA-256 and checks stored canonical bytes before a snapshot can be used. A digest provides one-way integrity; it is not encryption of arbitrary confidential information. Snapshots must contain only safe display data and complete supported parameters, never tokens/passwords/provider secrets.

An explicit exact org/Team/action-type/risk grant is required for either ADMIN or MEMBER. Existing membership alone grants safe reads. The narrow MEMBER transport exception covers only POST approve/reject paths, with CSRF and service-level fresh authorization. Revocation, expiry, disabled/version-stale accounts, self-decisions, missing human requester, moved requester Agent, inactive parent/action, snapshot corruption or current-head mismatch deny new decisions. A verified historical decision remains readable after head changes; it does not authorize the new action. No execution token is issued.

Concurrency follows the existing organization-first write protocol, then current human account/membership, action/request/snapshot/grants and parent checks. This intentionally serializes writes within an organization as existing creation services do; high-load scalability and finer-grained lock refactoring are not accepted by this slice. Future revocation/producer writers must use compatible ordering. Fresh authorization/grants are checked before any receipt replay; an authorized exact replay returns the original immutable decision without re-executing effects. Snapshot/head expiry after the original success does not turn a receipt into authority for a new action.

Application/API immutability is the implemented boundary. Privileged database administrators and future internal writers must not edit accepted snapshots or decisions; table privileges, immutable-history storage and key-management hardening belong to deployment/producer design. Do not claim protection against a malicious database owner from SHA-256 alone. Back up the ledger and use forward migrations; there is no destructive automatic down migration.

Acceptance includes Google formatting/import checks, full backend tests, real PostgreSQL exact persistence/replay/concurrent/revocation/rollback checks, responsive real-backend browser tests and synthetic visual artifacts. Local Java networking and Chromium sockets were blocked in this workspace, so CI supplies runtime evidence.

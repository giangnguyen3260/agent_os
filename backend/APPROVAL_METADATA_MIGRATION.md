# V010 Approval Center metadata ledger

V010 creates `approval_requests` for the read-only Approval Center. There is no business-data seed or task-to-approval backfill. Existing tasks and earlier migration checksums are unchanged; Flyway applies V010 at startup. Existing deployments therefore begin with zero approval records, which is an actual storage result rather than a runtime statement that no action needs approval.

Each record requires an organization, Team, display-safe title/action type, risk and stored status. Mission and Task are optional; Task requires Mission. Composite foreign keys require same organization/Team/Mission/Task. The requester must exist in the same organization; reads additionally require its current Team to match before exposing requester ID/name. A moved or unassigned requester is displayed as unavailable, not attributed to another Team. Created/updated timestamps are stored, not inferred from task states. The timestamp/status checks and organization/status/order index apply on PostgreSQL and H2 acceptance paths.

This is not an executable approval artifact. Raw request payload, exact action snapshot/version/hash, grants, human decision actor/reason, execution-run linkage and enforcement are outside this migration. Display metadata must not contain credentials, secrets or private payloads. No API accepts inserts or updates in this slice. A future Governance writer must add and enforce its own immutable action-binding, eligibility, decision/idempotency and execution revalidation contract before it can authorize any action; the `APPROVED` display value alone is insufficient.

Reads use explicit DTO fields, fresh enabled/versioned human membership authorization, stable bounded pages and a repeatable-read snapshot for counts/rows. MEMBER and ADMIN may read this safe organization metadata; neither receives approval decision rights from this migration. Needs information is a distinct stored state. The Decided group also contains expired, cancelled and invalidated records, which must retain their individual labels and never be described as approved decisions.

Rollback is not an automatic destructive down migration. Back up and follow the deployment's forward-migration procedure; do not drop the ledger after it contains real records. Future payload/security design should use additive migrations and preserve the safe-list projection. Run the isolated PostgreSQL fixture/probe plus the full Quality/Docker/browser gates before accepting changes. Test fixture SQL under scripts is disposable CI setup, not a production bootstrap or authorized manual production writer.
